# OJS 3.5.0-6 on the Keel LNMP image: a new install, the PKP checklist, the plugins and the maintenance mark

Date: 2026-11-10

This file is the evidence for the places marked "(second test)" in
decision note 0084. It covers test 1 of that note, the open parts of
test 5, and the maintenance mark, the worker and the scheduler of
section 7. It is a test by hand. No package was built. It is not a
commissioning test (0075).

## The question

1. Does a new install of OJS 3.5.0-6 pass on PHP 8.4 and MariaDB 11.8,
   in the layout of note 0084, and does the PKP checklist pass in a
   browser?
2. Does the install need the network?
3. Does `plugin_gallery_urls = '[]'` empty the gallery, and what does a
   plugin upload do on a read-only code tree?
4. Does a plugin that root copies, with `installPluginVersion.php`, give
   the same database state as a gallery install?
5. Does a plugin in a local directory load?
6. Does one file make nginx answer 503 with no reload, and how do the
   worker and the scheduler stop?
7. Which network connections does a running site make, and what happens
   when the network is not there?

## 1. The new install

The installer ran as www-data, with a `config.inc.php` that www-data
cannot write:

```
php tools/install.php     (answers on standard input)
```

| Run | Network | Code | Duration | Tables | ROR rows |
|---|---|---|---|---|---|
| First | yes | 0 | 106.3 s | 132 | 146716 |
| Under strace | yes | 0 | 76.0 s | 132 | 146716 |
| `unshare -n` | none | 0 | 12.7 s | 132 | 0 |
| nftables drop of outgoing packets | none | 0 | 11.8 s | 132 | 0 |
| DNS server that does not answer | none | 0 | 45.3 s | 132 | 0 |

The sha256 of `config.inc.php` was the same before and after each run.
`installed` stayed `Off`, and root set it to `On` after.

The 76-second run, from the strace times:

| Part | Time |
|---|---|
| Schema and data | about 12.5 s |
| Download of the ROR zip (39,263,398 bytes, from zenodo.org) | 28.3 s |
| Extract and import of the ROR data | about 29 s |
| Download of the IP database (db-ip.com) | 0.7 s |
| Unpack of the IP database | about 2 s |

So about 45 seconds of the 76 are local work. The first test said that
most of the install time is download. That was wrong.

With no network, the installer writes `cURL error 6` for
`download.db-ip.com` and `zenodo.org` and continues. The scheduler has a
task for each data set: `UpdateRorRegistryDataset` (`0 0 1 * *`) and
`UpdateIPGeoDB` (`0 0 10 * *`). The test did not run these tasks.

The installer cannot write the read-only file, so it prints what it
wanted to change. The first boot must write these values:

| Key | Installer value | Template value |
|---|---|---|
| `app_key` | a new key (as in the first test) | empty |
| `allowed_hosts` | `"[\"\"]"` | `''` |
| `time_zone` | empty | `"UTC"` |
| `enable_beacon` | `Off` | `On` |

A second instance with a config that www-data can write got
`allowed_hosts = "[\"\"]"` from the installer. Then each request gave
HTTP 400 until root set the host name.

The new database has the default `utf8mb4` / `utf8mb4_unicode_ci`. All
132 tables are InnoDB with `utf8mb3_general_ci`
(`connection_charset = utf8`). There is no mix of collations, different
from the imported database of the third test.

The PHP log of the install command has 48 deprecation messages.

## 1. The PKP checklist and the editorial flow

Source of the checklist: the upgrade guide, step 11, in `pkp/pkp-docs`
at commit `58079b5`. A browser did each step.

| Step | Result |
|---|---|
| Reader pages | Each public page gives 200. The crawl found one "broken" link, the RSS feed, which is a download |
| Registration, login | Passes. With email validation on, see defect 2 |
| Roles | A role invitation (Reviewer), "Login As", a profile change and a merge of two users pass |
| Submission to publication | A submission with a PDF, the editor decisions, an issue, a galley, the schedule and the publication pass. The database shows the issue and the publication as published at 19:24:24Z |
| Unpublish | The article was unpublished and the issue removed. The article page then gives 404 to a reader |
| Database | See the character set above |

Three browser steps ended with a timeout of the script (save of the
journal contact, "Activate Account", the confirm button of the merge).
The database shows that the contact was saved and that the merge was
done. The second try of "Activate Account" passed.

**Defect 1, nginx.** The `mime.types` of nginx 1.26 has no `mjs`. nginx
sent `pdf.mjs` as `application/octet-stream`, the browser refused the
module, and the PDF viewer was empty. With this rule, the type is
`text/javascript` and the viewer shows the PDF:

```
location ~ \.mjs$ { types { text/javascript mjs; } }
```

**Defect 2, OJS.** With `require_validation = On` and a journal that
has no support contact, a registration gives a PHP fatal error:

```
Symfony\Component\Mime\Exception\LogicException: An email must have a
"From" or a "Sender" header   (via ValidateRegisteredEmail.php)
```

The page tells the user that a message was sent. No message is sent,
and the account stays disabled.

After the journal got a technical support contact (Settings, Journal,
Contact), a second registration sent the message "Validate Your
Account", with the support contact as the sender. The link of that
message activated the account (`disabled` went from 1 to 0). The test
set `require_validation` back to `Off`, the default of the template,
13 seconds before the click that activated the account. So the
activation with the setting `On` at that moment is not shown.

PHP log during the flow (19:03:11Z to 19:31:44Z): 1 fatal error (defect
2) and 10 warnings, all `Undefined array key "invitation_id"` in
`InvitationModel.php` line 95. The log of the full session has 1636
warnings; most of them come from the plugin upload below.

The image has a fence (`turnkey-init-fence.service`) that redirects the
web ports until the first-boot questions are answered. The test stopped
the fence for the browser.

## 3. The gallery and the upload

`[security] plugin_gallery_urls = '[]'`:
- The gallery tab shows "No Items".
- A packet counter (nftables) for the addresses of pkp.sfu.ca stayed at
  0 during the gallery test.

Upload of `pln-v4_0_1-0.tar.gz` through the form of the plugins page,
on the read-only tree:
- Both POST requests answer 200 with `{"status":true,...}`.
- The page shows no message and no dialog.
- No plugin directory, no `versions` row, no new row in
  `notifications`.
- The PHP log gets 833 warnings (`mkdir(): Permission denied`,
  `copy(): Failed to open stream`).

So the upload does no harm, but the operator sees no error. The first
test called the install function from the command line and got a clean
error text. The form does not show that text.

## 4. A plugin as files, with `installPluginVersion.php`

The plugin: PLN 4.0.1.0 from the gallery list.

Reference: a second instance (`/srv/ojs2`, its own database, a tree
that www-data can write) installed the plugin from the gallery.

Read-only instance: root copied the files, then:

```
runuser -u www-data -- php lib/pkp/tools/installPluginVersion.php \
    plugins/generic/pln/version.xml
rc=0 duration=.352s
```

| Check | Result |
|---|---|
| `versions` row | The same: `plugins.generic pln 4.0.1.0`, `current = 1`, class `PlnPlugin` |
| Plugin tables | The same: `pln_deposit_objects`, `pln_deposits`. A `diff` of their schema dumps is empty |
| Full schema dump | 2 lines differ: the database name |
| `plugin_settings` | No row in each instance, before the plugin is enabled |
| Enable in the browser | `plugin_settings` then has `enabled = 1` |

The gallery copy of the plugin does not have one directory that the
tarball has (`vendor/symfony/string/Resources/bin`).

**The exit code** (read from the code of 3.5.0-6, not run):
- The tool ends with `exit(1)` when the argument is missing or the file
  does not exist.
- `execute()` writes the `versions` row before it runs the plugin
  migration.
- `Plugin::updateSchema` catches an exception of the migration and
  returns false.
- The script calls `$tool->execute();` and does not use the result.

So a plugin migration that fails leaves the `versions` row and an exit
code of 0. A `postinst` must not trust the exit code only.

## 5. A local plugin directory

`/usr/share/ojs/plugins/generic/customHeader` was a link to
`/var/lib/ojs/plugins/customHeader` (customHeader 1.0.5.1).

| State | Listed on the plugins page |
|---|---|
| Files as the tarball unpacks them as root (directories 0700) | No |
| After `chmod -R a+rX` and `installPluginVersion.php` | Yes, can be enabled, its hook runs |
| The same, with the `versions` row deleted | Yes |

The file modes of the tarballs are not safe to keep: customHeader
unpacks to 0700, PLN unpacks to 0777. A package must set the modes.

The plugin itself gives a `TypeError` on each page when it is enabled
with no header text (`addHeader(): Argument #2 ($header) must be of
type string, null given`). OJS continues. The test disabled it after.

## 6. The maintenance mark, the worker and the scheduler

The nginx rule of the test:

```
set $ojs_maintenance "";
if (-f /var/lib/ojs/maintenance) { set $ojs_maintenance 1; }
if ($uri = /keel-health) { set $ojs_maintenance ""; }
if ($ojs_maintenance) { return 503; }
error_page 503 @ojs_maintenance;
location @ojs_maintenance {
    add_header Retry-After 300 always;
    add_header Cache-Control "no-store" always;
    default_type text/html;
    return 503 "<!DOCTYPE html>...The journal is in maintenance...";
}
location = /keel-health { try_files /.keel-health-is-no-file =204; }
```

With `touch /var/lib/ojs/maintenance` and no nginx reload: the pages,
`/api/`, a POST, a static `.mjs` file and `/public/` give 503 with
`Retry-After: 300`, in about 1 ms. `/keel-health` gives 204. After the
file is removed, the next request gives 200 (or 401 for the API), again
with no reload.

The same nginx file gives 403 for `config.inc.php`, `cache`,
`dbscripts`, `tools`, `classes`, `registry`, `locale`, `jobs`, `docs`,
for `.tpl`, `.po`, `.xml` and `.inc.php` files, for dot files, and for
each `.php` file that is not `index.php`.

**Worker.** A systemd unit ran `php lib/pkp/tools/jobs.php work` as
www-data, with `Restart=on-failure`.
- `jobs.php restart` while job 1 ran (a table lock held the job):
  the worker completed job 1, then stopped. systemd shows "Deactivated
  successfully", `ExecMainStatus=0`, `NRestarts=0`. 9 jobs stayed in
  the queue and 0 failed. systemd did not start the worker again.
- After a new start, the queue was empty in 2 seconds, with 0 failed
  jobs.
- `systemctl stop` of an idle worker took 0.05 seconds.
- `jobs.php restart` writes its signal as a file in the cache
  (`/var/cache/ojs/opcache/...`, 23 bytes).
- The worker wrote 8 messages "Skipped indexation: No suitable parser"
  for the PDF. The template has the `index[application/pdf]` line as a
  comment, and the image has no `pdftotext`.

**Scheduler.** A systemd timer ran `php lib/pkp/tools/scheduler.php
run` each minute. `scheduler.php list` shows 15 tasks. A job in the
queue stayed there with `process_jobs_at_task_scheduler = Off`, so the
scheduler does not do the work of the worker. Version 3.5 has no table
`scheduled_tasks`.

The worker and the timer are separate processes. The nginx mark does
not stop them.

## 7. The running site and the network

With the network: the only outgoing traffic of the site was DNS and one
address on tcp 443, that of pkp.sfu.ca. It is the version check:

```
https://pkp.sfu.ca/ojs/xml/ojs-version.xml?id=<uuid>&oai=<url>
```

Three administration pages make it (the administration index, the
system information and the site settings).

| Network state | Result |
|---|---|
| Outgoing packets refused (a fast failure) | Each page gives 200 at the usual speed. The 3 administration pages write "Failed to retrieve the latest version info: cURL error 6" |
| DNS server that does not answer | Each page gives 200. The public pages with journal, issue or article content take 6.3 to 6.5 s, the login 6.0 s, the 3 administration pages 12.7 to 13.3 s. The other pages have the usual speed |

In the second state, strace shows that PHP-FPM asks the DNS server for
the name of the client address (a PTR query), and waits two times 3
seconds. The test did not find which OJS code does this.

pkp.sfu.ca and `download.db-ip.com` had no AAAA record on the test
day. The container reached them by IPv4.

## What this does not show

- An IPv6-only node. The container had IPv4. The version check and the
  IP database download go to hosts with no AAAA record.
- A plugin migration that fails with `installPluginVersion.php`. The
  result above is from the code.
- The code that makes the reverse DNS query, and a setting that stops
  it.
- `systemctl stop` of a worker in the middle of a job, and a cache
  clear while a worker runs.
- The two scheduled tasks that get the ROR data and the IP database
  after an install with no network.
- An account activation while `require_validation` is `On` (defect 2).
- PDF indexing with `pdftotext`.
- The package, `preinst`, `postinst` and `ojs-upgrade`.
- A pair, Syncthing, and a slow link (netem).
- A large journal.

Items from the report of the test that the coordinator did not compare
with the logs line by line: 15 JavaScript errors on the form that makes
a journal, some help labels with no translation, a search that gives 0
results until the worker runs, and the correct display of Portuguese,
Greek and Japanese letters.

## Deviations

- The test destroyed CT 9365 and made it again one time, 60 seconds
  after the first create. `pct push` refused a stopped container, and
  the first start had no preseed file. Nothing of the test was in the
  container at that time.
- The container had an IPv4 address from DHCP. The plan was an
  IPv6-only container.
- The report of the test said that the upload makes an error
  notification, and that the plugin tool gives code 0 for a bad path.
  The logs do not show this (sections 3 and 4), and this file does not
  say it.

## State after the test

CT 9365 is stopped and not removed. The test deleted its answer files
and its install outputs in the container. Nothing was published. The
command logs and 91 screenshots are with the coordinator; this file
holds the lines that the note uses. The coordinator compared the report
of the test with the logs before this file was written.
