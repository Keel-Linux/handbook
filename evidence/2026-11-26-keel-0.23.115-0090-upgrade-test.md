### Method

Stages on each node (`run.sh`):

- A: the node as made from the published image (keel 0.23.96; Nextcloud

- B: `apt-get upgrade` from `trixie`, `trixie-testing` off: keel 0.23.98,

  The baseline.
- C: the six candidates (above). Just before and just after the install:
  the InvocationID of each unit, the firewall facts, the fence facts. No
  apply in C.
- E: an attended apply, `keel spec apply --system` (the command a person

- F: `pct reboot`, 60 s of wait, the same facts.

after E and after F: TCP connect to 22, and one HTTP(S) request to 80, 443
and 12321 that reads the body (`FENCE` when the body is the init fence page).
A failed unit after the install stops the run of that node.

### keel diff and decision "A"

On each of the 13 nodes the diff of stage C (after the install, before any
apply) has these new drift lines, and no other change from stage B:

- `derived.monit: drift (declared the file apply renders from the manifests, observed a file that differs from it)`
- `derived.firewall: drift (declared the ruleset apply renders from the manifests, enforce, observed nothing)`
- `derived.firewall.loaded: drift (declared <digest>, observed nothing)`

`derived.firewall.state` (not compared) says "an apply a person runs
(keel spec apply --system) writes enforce", and `derived.firewall.listeners`
(not compared) names each socket that enforce closes: TCP and UDP 12321 of
Webmin on each node, and the random TCP port of Syncthing on the 8 nodes
with Syncthing. Thus the diff foretells `enforce` (keel#318).

The attended apply then wrote exactly `derived.monit` and `derived.firewall`
on each node, and also `overlays.syncthing` on web, lnmp, lnpp, laravel,
wordpress, odoo, nodebb and nextcloud: it rewrote
`/var/lib/syncthing/config.xml` and `/var/lib/keel/filesync/render.sha256`
and restarted `syncthing.service`. The diff of stage C said
`overlays.syncthing: same (enabled)`. The published images have
`listenAddress tcp://:0`; keel 0.23.100 and later render
`tcp://127.0.0.1:22000` when there is no overlay address, and `keel diff`
does not compare the render digest. This is defect **keel#347**. On these
one-node nodes it has no effect for a user.

Two more points, by design:

- The digest that the diff declares for `derived.firewall.loaded` differs
  from the digest that the attended apply loads. The apply also closes IPv4
  22 (decision 0098, answer 6), and the diff keeps what keel's file says of
  IPv4 22, because the close is a person's act and not a field of the spec
  (`foretell`, `keel/system/firewall.py`, "keel diff passes False"). So the
  diff does not say in words that IPv4 SSH closes.
- The drift of stage B stays after the apply, so `keel diff` right after the
  apply gives exit 0 on 3 of 13 nodes only (core, ntfy, redis) and exit 14 on
  the other 10: `database.server.role` (declared primary, observed
  standalone, a one-node node; 9 nodes with a database) and the `filesync.*`
  folder and peer lines of a one-node node with Syncthing (8 nodes). The apply
  does not change these fields. They come from the instance descriptions of
  the test: the 0.23.100 test has the same lines in its stage B (lnmp:
  `database.server.role`, `filesync./var/www/keel-default.folder`,
  `filesync.peer`; mariadb: `database.server.role`; web: the 2 `filesync`
  lines).

After the reboot (F) there is also the known `instance.fqdn` drift of the
Proxmox block of `/etc/hosts` (finding 2 of the 0.23.98 test).

### The init fence

On core and web the instance description leaves a question to keel-init
(75keel-role: "confconsole's role screen has a question: keel-init asks
it"; the descriptions have no database section), so the fence stays up
after the first boot by design. This is also true of the earlier tests,
which did not probe from outside.

| Node | Before C | After C | After F |
| --- | --- | --- | --- |
| core, web (keel-init not run) | fence on iptables (inithooks +keel38): fence page on 80, 443, 12321 | `turnkey-init-fence.service` enabled, table `inet keel_fence` present (the fence of +keel41 on nftables); fence page on 80, 443, 12321 | the same, and `ct status dnat` accepted in `inet keel` |
| the other 11 (keel-init done) | fence disabled | fence disabled, no `inet keel_fence`, no `ct status dnat` rule | the same |

So the inithooks upgrade moves a fence that is up to nftables, and makes no
fence on an initialised node. The probe ran before and after the install,
not during it, so it does not show the ports during the install (round 2
measured that, A1 "#68 case").

### Defect inithooks#73: a failed unit after the inithooks upgrade

On web (9403) and nextcloud (9414) the install left
`inithooks-restart-getty1.service` failed and the node `degraded`:

```
restart-getty[9643]: inithooks.service running - waiting 10 more seconds for it to stop
restart-getty[9643]: inithooks.service did not stop - no getty started
systemd[1]: inithooks-restart-getty1.service: Failed with result 'exit-code'.
```

The preinst stops `inithooks.service`; its `ExecStopPost` starts
`restart-getty`, which waits 10 s for `inithooks.service` to stop; the
postinst starts `inithooks.service` again in that time. On the other 11
nodes `restart-getty` won the race and started `container-getty@1.service`.
The failed unit stays until the next reboot (web: `degraded` in C and E,
`running` in F). The run of these 2 nodes stopped after C by the rule of the
test, the failed unit was looked at, and the run went on from C
(`resume.sh`). The checks of the application pass. Filed as inithooks#73.

### Verdict

Across a failover and a failback at about 250 ms with netem on both pair
nodes after each start, the rejoining old primary refused each write with
error 1290 and read `read_only = 1` in each local reading, from its first
answer until it held the VIP again. No write was accepted on a node that
did not hold the VIP. The reading of round 2 (`kc9420 0` at 11:43:26) did
not come again. This agrees with the code study on the issue: both nodes
start read only, and only the promotion sends `read_only = OFF`. keel#343
is closed with this evidence.
