# Pixelfed 0.15.2 on the Keel LNMP image: the first test by hand

Date: 2026-11-12

This file is the evidence for decision note 0088. It is a test by hand on
one container. No image and no package was built. It is not a
commissioning test (0075). The node did not federate with a real
instance, and it was never reachable as a public instance.

## The questions

1. Does Pixelfed install and run on Debian 13, PHP 8.4 and MariaDB 11.8,
   with no Docker?
2. Which nginx rules does it need on the route directory of Keel Web?
3. Which paths, rows and keys hold state?
4. How much CPU, memory and disk does an upload use?
5. Which federation endpoints answer, signed and unsigned?
6. What happens with a read-only database and with an empty Redis?
7. Which outgoing calls does it make?
8. Does the upgrade method of upstream work from the previous release?
9. Do the hook and the gate of the prototype `keel-pixelfed` work on a
   real node?

## The firewall of the test

After the install, an nftables table (`files/pftest.nft`) dropped every
new packet in and out, except the loopback, answers, ICMPv6 and DNS. It
kept the destination of each dropped packet. For the upgrade, a second
table (`files/pftest-open.nft`) let packets out and kept their
destinations. The table does not survive a reboot: after the reboot of
item 11 it was loaded again (`62-reboot.log`).

### 5. Federation endpoints

Federation was off after the install, as upstream sets it. The switch that
counts is the row `federation.activitypub.enabled` of the table
`config_cache`. The first page view wrote the row from `.env`
(`ACTIVITY_PUB=false`). After that, `ACTIVITY_PUB=true` in `.env` changed
nothing: the row wins, and Pixelfed keeps the value in its Redis cache for
12 h. The row set to 1 and `cache:clear` turned federation on
(`36-actors-inbox.log`).

| Endpoint | Federation off | Federation on | Log |
|---|---|---|---|
| `/.well-known/nodeinfo`, `/api/nodeinfo/2.0.json`, `/.well-known/host-meta`, WebFinger of a user and of the instance | 200 | 200 | `33-start.log`, `35-federation-on.log` |
| `/i/actor`, `/i/actor/outbox` (instance actor) | 200 | 200 | `36-actors-inbox.log` |
| `/users/keeladmin` with an ActivityPub Accept header | 302 to the profile page | 200, `application/activity+json` | `36-actors-inbox.log` |
| `/users/keeladmin/outbox`, `/followers` | 404 | 200 | `36-actors-inbox.log` |
| POST, no signature, to `/f/inbox`, `/users/keeladmin/inbox`, `/i/actor/inbox` | 404, 404, 200 | 200 each; no follower, no remote profile | `36-actors-inbox.log` |
| POST with an HTTP signature (Cavage, rsa-sha256) of a made-up actor at `remote.keel.invalid` | | 200 each in 0.04 to 0.06 s. The inbox puts the activity on the queue; `InboxWorker` and `InboxValidator` then drop it (the key cannot be fetched). No follower, no failed job | `37-signed-inbox.log` |

The public key of the user actor is the row `profiles.public_key`, and that
of the instance actor is the row `instance_actors.public_key`: the sha256
of each document key is equal to that of its row (`36-actors-inbox.log`).
No ActivityPub key is a file.

### 12. MariaDB and upstream issue #6082

Issue #6082 (MariaDB 10.11, 2025) reports that reblogs broke because
`statuses.caption` was `NOT NULL`, and that `DB_CONNECTION=mariadb` broke
the location search with an `ONLY_FULL_GROUP_BY` error. On this install
`caption` and `rendered` are also `NOT NULL`. A reblog, an unreblog and a
location search gave 200 with `DB_CONNECTION=mysql` and with `mariadb`
(`44-mariadb-issue-6082.log`). The search returned places, so the branch
with the `GROUP BY` (with no query) did not run. That branch was not
tested.

### 13. The OAuth token of the administrator

The first personal access client had id 1, and the administrator had id
1. The API refused the token (401). Passport 13 reads a token as a client
credentials token when the user id is equal to the client id and the
client has the grant type `client_credentials`. The table `oauth_clients`
of Pixelfed has the old columns with no `grant_types`. A second client
(id 2) gave a token that works (`40-upload-prep.log`). This was seen with
a personal access client only. An application client with id equal to a
user id was not tested.

## What was not tested

- A pair in cloud advanced, a promote, Syncthing on the media, 250 ms.
- Anubis and Coraza in front of Pixelfed (the front file of the prototype).
- Federation with a real instance, a remote follow, delivery and its retry.
- A Redis that is read only (a replica Redis). Redis runs alone on each
  node by the maintainer's rule, so it was not needed.
- Object storage (S3).
- A video transcode (Pixelfed does none) and the upload of a large file.
- A mobile application and the authorization code flow of OAuth.
- The build of the image (`conf.d/main`), the image and the 0075
  commissioning.
- Load: many users, many remote instances, queue floods.
