# keel 0.23.62 to 0.23.68 on live pairs, MariaDB and PostgreSQL

Date: 2026-11-01. The time zone is UTC. No secret is in this file.

This test gives data for the decision to promote keel 0.23.68 and
keel-mariadb 0.1.1 to `trixie`. It did not promote a package.

## Result

**The upgrade itself passes. Do not promote until the two findings below
have a decision.**

| Finding | Severity | Effect |
| --- | --- | --- |
| After the upgrade, a container whose spec says `network.managed_by: file` fails `keel spec apply` (exit 16) and shows drift in `keel diff` (exit 14) | High | All 6 CTs. The spec came from `keel inspect` on 0.23.62. See "Finding 1" |
| keel#242 lost 1 acknowledged write on a MariaDB holder that still ran 0.23.62, during the mixed state | Known defect, real effect on the order of the upgrade | See "Finding 2" |

| Run | Engine | Order | Acknowledged writes | Lost |
| --- | --- | --- | --- | --- |
| A | MariaDB | W, replica, holder | 2521 | 0 |
| A | PostgreSQL | W, replica, holder | 4713 | 0 |
| B | MariaDB | holder, then mixed state, then replica, W | 12722 | **1 (id 1357, on the 0.23.62 holder)** |
| B | PostgreSQL | holder, then mixed state, then replica, W | 3014 | 0 |

No write was lost on a holder that ran 0.23.68: 5 crashes on each engine in

## Finding 1: `keel spec apply` refuses after the upgrade

On all 6 CTs, after the upgrade to 0.23.68:

```
network.managed_by: drift (declared file, observed host)
keel diff: exit 14

network: differs: network.managed_by
network: refused: declared managed_by: file, but this is a container, whose host writes its interfaces
apply --system-only: 0 change(s), 1 failed
keel spec apply: exit 16
```

Before the upgrade, `keel diff` returned 0 on the same specs. In the mixed state
only the upgraded node had the drift. This comes from keel#238 (0.23.65): keel
now reads the container record of systemd. The specs came from `keel inspect`
on 0.23.62, which writes `file` on these CTs.

Effect: a running pair stays healthy, with no failed unit, and failover and
promote work. But an operator cannot apply a change to the spec until the spec
changes, and a monitor that reads `keel diff` sees drift on each container.

The remedy, checked on 9330 only: change the line to `managed_by: host` by hand.
`keel diff` then returned 0. No package does this change, and no note tells an
operator to do it. The earlier test of 0.23.68 did not see this, because it
wrote the spec after the upgrade.

## Finding 2: keel#242 is real for as long as a holder runs 0.23.62

Round 2 of the mixed MariaDB run killed the holder C, on 0.23.62:

```
t0   1793522242.39  SIGKILL of mariadbd on C
     1793522250.06  writer: insert of id 1357 starts
     1793522250.29  first poll that saw read_only = 0 on C
     1793522251.30  cut of C
     1793522251.54  writer: id 1357 acknowledged
```

B, on 0.23.68, became the holder without the row. When C was healed:

```
refused: diverged: this node holds 1 transaction(s) the holder lacks
(domain 0, server id 1512866743, up to sequence 1257). It stays read only and is not connected
```

keel behaved as designed for that version: it did not let C rejoin, and it
kept a dump each time. The dump `rejoin-20261101T090455Z.sql.zst` on C holds the
row: `(1357,'2026-11-01 08:37:31')`. C stayed out for 25 min, until the test ran `keel spec
apply --system-only --destroy-local-database` (36 s). `keel-database-follow.service`
was failed during that time. So a crash and a cut together can lose a write on
each holder that is not upgraded yet. The upgrade closes this, so a fleet must
move all its pair nodes in a short time.

The test forced this timing, with `keel database follow` at once and a cut
1 s later. It is the same worst case as the keel#242 evidence.

Side effect: while the node stayed diverged, keel wrote one dump for each run of
the watch, about each 30 s. C held 53 dumps and 27 MB at the end of the run. The
data is small here. On a large database this can fill the disk. This is not
checked further.

## Other observations

- **A new mesh on 0.23.62 can stop on W.** In 2 of 2 formations of MariaDB and
  1 of 2 valid formations of PostgreSQL, `keel mesh members` on W waited
  in `systemctl start keel-vip.service` for minutes while it held
  `/var/lib/keel/mesh/sync.lock`. keel-vip waited for etcd, and etcd on W
  had no peer C, because `keel mesh sync` could not take the lock. `keel diff`
  showed a missing peer. `systemctl restart keel-mesh-members` and `keel mesh
  sync` cleared it each time. The test did not check if 0.23.68 still has
  this. No such stop happened in the earlier 0.23.68 setup, 1 formation only.
- **A new PostgreSQL replica needs the reseed flag.** The first apply on C
  refuses ("diverged"), because the new node has its own cluster. `keel spec
  apply --system-only --destroy-local-database` seeds it. This is the design.
- **One `apt-get update` took about 5 min on C** (MariaDB, run B), and the
  package install 28 s. The others took seconds. The cause was not found.

## What went wrong in the test

These are errors of the test, not defects of the product.

- A shell function named `cut` hid the `cut` command, and one call tried `tc` on
  BR1 with the device `vethi0`. The device does not exist, so the command failed
  and nothing changed. The function has a new name.
- `waitready` read a database that did not exist yet, so the first PostgreSQL
  run A stopped with "NOT READY" before it did anything. It ran again.
- The labels of the first MariaDB run A say `upgrade-c` for all 3 upgrades,
  because of a variable with no `local`. The table above uses the order of the
  marks: W, replica, holder.
- The first PostgreSQL rebuild for run B had no `apt-get update`, so it stayed
  on 0.23.56 and did not get ready. It was destroyed and built again. No result
  of it is in this file.
- The script for run B of MariaDB ended at the stuck round. The rest of the
  run came from a second script. After the first reseed, that script called
  `up` for the holder B again. This was a no-op, because B was on 0.23.68.
- The holder's server starts late on some rounds, so the time from the kill to
  the cut is longer on PostgreSQL. This changes no count.

## What this test does not show

- keel 0.23.68 does not have the open fixes for keel#167, keel#190, keel#191,
  keel#107, keel#252 and decision 0070, or keel#110 in 0.23.69.
- No application ran on the pairs: no WordPress, no Odoo.
- The upgrade was only `keel`, from `trixie-testing` with `apt-get install
  --only-upgrade keel=0.23.68`, not `apt full-upgrade` from a promoted `trixie`.
- Case 4 was not repeated at the end of run B. Run B ended with the upgrade
  and its checks.
