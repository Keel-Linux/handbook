# Evidence: PowerDNS 5.1 on PostgreSQL hot standbys, and the failover record (decision 0045)

Date: 2026-11-23. Site: BR2, the Keel test VM (nested Proxmox VE, VM
101). Status: laboratory test, for decision 0045 (second round,
handbook#201, proposed). This file answers the items of 0045 that are
"not verified" or "to test". It does not change the note.

## Questions

- **Q1.** Does the Debian source package `pdns` 5.1.5-2 of forky build
  on trixie (amd64)? Which changes are necessary? Do its build-time
  tests and lintian pass?
- **Q2.** Does PowerDNS Authoritative 5.1 with `gpgsql` serve correctly
  from a read-only PostgreSQL hot standby? The zones are a plain zone, a
  zone that is signed live, and LUA records. Which settings are
  necessary? Does a query path try to write? Do replication conflicts
  cancel queries? What happens when the writer stops, and when a
  standby loses the replication?
- **Q3.** How fast does the failover record of 0045 section 10 E move,
  step by step? This includes the cold start, the case where all
  addresses fail, a redirect, and a DNS server that cannot reach the
  web nodes.
- **Q4.** Does `ifurlup` reach the right node through a TCP proxy that
  routes by SNI? What does the check see when the proxy is up and the
  node behind it is down?

The coordinator added review points to Q2 and Q3. They are: the cold
start query by query, redirects, `api-readonly`, the packet cache, NSEC,
a DNS server with no path to the web nodes, and each step of the switch
time.

## Short answers

- **Q1: yes.** The forky source builds on trixie with no change to the
  source and no package from trixie-backports. The build-time tests
  pass. lintian gives 0 errors and 2 warnings.
- **Q2: yes.** A hot standby serves the plain zone, the zone that is
  signed live, and the LUA records. Every answer of the signed zone
  validated on the writer and on both standbys. The exception is the
  first query for a LUA name after a start (SERVFAIL, Q3). No query path wrote:
  the standby PostgreSQL logs show "read-only transaction" errors only
  for the 2 write acts that this test made on purpose. Replication
  conflicts cancelled no PowerDNS query. `VACUUM FULL` on the writer
  delayed up to 0.21 % of the answers beyond 2 s. `api-readonly` does
  not exist in 5.1.5, and a file that sets it stops `pdns` at start.
- **Q3:** when the old primary's check address refuses or answers 404,
  a DNS server gives the new primary only 5.5 s to 12.4 s after the
  change (7.6 s to 14.4 s from the start of the act). For a node that
  powers off, it is 9.7 s to 13.9 s (14.2 s to 18.9 s). The note
  estimates 7 s. The
  measured time is 2 failed checks with `minimumFailures=2`, and a
  check that times out runs only every 10 s. For about 5 s (10 s for a
  timeout) in each switch, every server gives both addresses.
- **Q4: yes.** Through an HAProxy in `mode tcp`, `ifurlup` reaches the
  node that the proxy selects by SNI and reads that node's answer. When
  the proxy is up and the node behind it is down, the check sees a
  timeout and marks the proxy address down.

## Q2: PowerDNS 5.1 on PostgreSQL hot standbys

### The settings

All 3 servers use the same `pdns.conf`. Only `local-address` changes:

```
launch=gpgsql
gpgsql-host=127.0.0.1
gpgsql-dbname=pdns
gpgsql-user=pdns
gpgsql-password=REDACTED
gpgsql-dnssec=yes
local-address=127.0.0.1, ::1, <IPv4 of the CT>, <ULA of the CT>
primary=no
secondary=no
api=no
webserver=no
enable-lua-records=yes
lua-health-checks-interval=5
lua-health-checks-expire-delay=86400
loglevel=6
log-timestamp=yes
include-dir=/etc/powerdns/pdns.d
```

Each PowerDNS reads only the PostgreSQL of its own CT, on the loopback.
On a standby, PostgreSQL listens only on the loopback. The defaults of
5.1.5 that matter here: `cache-ttl=20`, `query-cache-ttl=20`,
`negquery-cache-ttl=60`, `dnssec-key-cache-ttl=30`,
`zone-metadata-cache-ttl=60`, `zone-cache-refresh-interval=300`,
`enable-lua-record-updates=no`, `consistent-backends=yes`.

- **`primary=no`, `secondary=no`, `api=no`** were enough. With these,
  the standbys logged no PostgreSQL error from a query (below).
- **`api-readonly`** does not exist in 5.1.5. `pdns_server
  --api-readonly=yes` says "Fatal error: Trying to set unknown setting
  'api-readonly'". The same line in a file under `pdns.d` makes
  `systemctl restart pdns` fail with the same message. The setting to
  use is `api=no`.
- **`enable-lua-record-updates=no`** (the default) does not stop
  `pdnsutil rrset add` from writing LUA records on the writer. The
  setting is not necessary for `pdnsutil`.
- **`include-dir`:** a `pdns.conf` that replaces the Debian file must
  set `include-dir`, or PowerDNS ignores `/etc/powerdns/pdns.d/`. The
  first pass of this test missed this. The results below that need a
  file in `pdns.d` come from the second pass.

### The zones

On the writer, `pdnsutil` made:

- `plain.test`: unsigned, 3 static records.
- `example.test`: signed live (`pdnsutil zone secure`: one CSK, ECDSA
  P-256, NSEC), static records, and the LUA records of Q3 and Q4.
- `load.test`: 4000 A records for the load of Q2.

`zone export-ds` gave `example.test. IN DS 53859 13 2 06af1ee6...1451`.
The client used this DS as a static trust anchor for `delv` (`-a`,
`+root=example.test`).

### Answers from the standbys

- **A new zone appears after the zone cache refresh.** Right after
  `pdnsutil zone create`, all 3 servers answered REFUSED, the writer
  too. Each server served the new zones 316 s to 320 s after its own
  `pdns` start, at its first zone cache refresh
  (`zone-cache-refresh-interval=300`). `pdnsutil` itself says "be sure
  to refresh its zone cache with 'pdns_control rediscover'".
  `pdns_control rediscover` on a standby answered "Ok" and logged no
  PostgreSQL error.
- **DNSSEC.** `delv` gave "fully validated" from each of the 3 servers
  for: `www` A and AAAA (LUA), the apex A and AAAA (LUA), `edge` A
  (LUA), `static` A, the `DNSKEY` set, a NODATA answer (`www` TXT) and
  an NXDOMAIN answer.
- **A LUA record at the zone apex works,** for A and AAAA, signed. The
  study listed this as not verified.
- **NSEC at a name with LUA records.** The NODATA answer for
  `www.example.test` TXT carries `www.example.test. NSEC example.test.
  A AAAA RRSIG NSEC`. The type bitmap shows the types that the LUA
  records make, not the LUA type (65402). The answer validated.
- **NSEC3 at a name with LUA records.** After `pdnsutil zone set-nsec3
  example.test '1 0 0 -'` and `zone rectify` on the writer, the NSEC3
  record of the hash of `www` has the bitmap `A AAAA RRSIG`. `delv`
  gave "negative response, fully validated" from all 3 servers for the
  NODATA answer (`www` TXT) and for an NXDOMAIN answer. The standbys
  gave NSEC3 answers 3.6 s and 26.5 s after the change.
- **The packet cache does not keep LUA answers.** With `cache-ttl=20`,
  10 queries for a static name gave 9 packet cache hits. 10 queries for
  a LUA name gave 10 misses and 0 hits (`pdns_control show
  packetcache-hit` and `packetcache-miss` on dns2).
- **A record change reaches the standbys** in 16.6 s to 22.1 s (2
  changes of `static` A, each standby asked once before the change).
  The writer, which had no cached answer, gave the new value after
  4.0 s to 4.5 s. That time includes the run time of `pdnsutil`.
- **A key change reaches the standbys** within the key cache time. The
  writer removed an active ZSK (`zone deactivate-key`, then
  `remove-key`). Each server stopped signing `www` with that key after
  21.1 s to 29.5 s, and removed it from the DNSKEY set after 32.9 s to
  42.8 s (`dnssec-key-cache-ttl=30`, plus the packet cache for the
  DNSKEY answer). Each server validated after the change. When a ZSK
  was added while the writer could not replicate, both standbys showed
  it less than 18 s after the replication came back.

### Write attempts

The PostgreSQL logs of both standbys hold no ERROR from a PowerDNS
query, from the setup to the end. This covers all the queries of this
file, more than 1 million. The only "read-only transaction" errors are
from 2 acts that this test made on purpose on dns2:

- `pdnsutil zone rectify example.test`: "cannot execute UPDATE in a
  read-only transaction".
- `pdnsutil rrset replace ... static.example.test ...`: "cannot execute
  DELETE in a read-only transaction".

### Replication conflicts

The test ran a write load on the writer and `dnsperf` against both
standbys at the same time: 800 queries per second, 4 clients, 120 s,
4000 names of `load.test`, timeout 2 s. Each run read
`pg_stat_database_conflicts` on both standbys before and after it. The
caches of PowerDNS were off on the standbys (`cache-ttl=0`,
`query-cache-ttl=0`, `negquery-cache-ttl=0`). Thus each query reached
PostgreSQL. dns2 counted 312350 backend queries for 100919 DNS queries.
`hot_standby_feedback` and `max_standby_streaming_delay` changed per
run. The write load was:

- **churn:** 400 deletes, 400 inserts and about 800 updates of
  `records` every 0.2 s, and `VACUUM records` every 25 rounds.
- **vacfull:** `VACUUM FULL records` every 3 s. This takes an
  AccessExclusiveLock, and the standby replays it.

| Run | `hot_standby_feedback` | delay on dns3 | Conflicts on dns2, dns3 | Answers on dns2, dns3 | No answer in 2 s |
| --- | --- | --- | --- | --- | --- |
| churn | off | 30 s | 0, 0 | 95530, 95458 | 0, 0 |
| churn | on | 30 s | 0, 0 | 95128, 95538 | 0, 0 |
| vacfull | off | 30 s | 0, 0 | 90963, 92278 | 194, 0 |
| vacfull | off | 0 | 0, 0 | 94619, 94886 | 0, 0 |
| vacfull | on | 0 | 0, 0 | 90688, 91144 | 97, 100 |

- All answers were NOERROR or NXDOMAIN. There was no SERVFAIL. The
  NXDOMAIN answers are names that the churn deleted.
- **No replication conflict cancelled a PowerDNS query,** also with
  `max_standby_streaming_delay = 0`. The PostgreSQL logs and the
  PowerDNS logs of the standbys have no error from these runs.
- **`VACUUM FULL` on the writer delayed some answers.** 0.11 % to
  0.21 % of the queries got no answer within 2 s. The probable cause
  is the replay of the lock on the standby. This test did not measure
  the cause.
- **Control:** on dns3, with `max_standby_streaming_delay = 0`, a read
  transaction that held `records` for 20 s was cancelled by the replay
  of `VACUUM FULL`: "canceling statement due to conflict with
  recovery", and `confl_lock` went from 0 to 1. The method thus sees a
  conflict. The short queries of PowerDNS do not hold a lock for long
  enough.
- **A database session that ends.** During 60 s of `dnsperf` against
  dns3 (caches off), the test ended the PowerDNS sessions with
  `pg_terminate_backend` every 5 s (25 sessions). PowerDNS logged
  "Backend error (retry once)" and connected again. All 47801 queries
  got an answer, and none was SERVFAIL.
- The first pass of these runs had the caches on, because `pdns.d` was
  not read. It gave 0 conflicts and 0 unanswered queries too.

### The writer stops, and a standby loses the replication

- **The writer CT stopped for 120 s** (`pct stop`). Both standbys kept
  their answers: `www` (LUA), `static`, `plain.test`. `delv` gave
  "fully validated" from both. The WAL receivers retried every 5 s and
  logged "could not connect to the primary server".
- **A defect of the test setup after the writer started again.**
  PostgreSQL on the writer started before the CT had its DHCP and SLAAC
  addresses. It logged "could not bind IPv4 address ...: Cannot assign
  requested address" and listened on the loopback only. The standbys
  stayed cut until a manual `systemctl restart postgresql` about 4 min
  later.
  A `listen_addresses` with fixed addresses needs the addresses before
  PostgreSQL starts. Keel must order this, or listen on `*` and limit
  access with `pg_hba.conf`.
- **dns2 lost the replication for 180 s** (a `prohibit` route to the
  writer inside dns2). During the cut, the writer changed `static` A.
  dns2 gave the old value for the whole cut, and dns3 gave the new one.
  `delv` from dns2 gave "fully validated". At the end of the cut, the
  replay lag of dns2 was 3 min 19 s. dns2 gave the new value 11.2 s
  after the route was removed, and the WAL receiver was `streaming`
  again.

## Q3: the failover record

### The record

The record follows 0045 section 10 E. Both families list both nodes:

```
www.example.test. 60 IN LUA A "ifurlup('https://www.example.test/.well-known/keel/primary', {'<web-a IPv4>', '<web-b IPv4>'}, {stringmatch='keel-primary fd00:db8::ffff:1', selector='all', backupSelector='all', failOnIncompleteCheck='true', minimumFailures='2'})"
www.example.test. 60 IN LUA AAAA "ifurlup('https://www.example.test/.well-known/keel/primary', {'<web-a ULA>', '<web-b ULA>'}, {...the same options...})"
```

The apex `example.test` has the same 2 records with the URL
`https://example.test/...`. The values used: `lua-health-checks-interval=5`
(the note), the check timeout 2 s (the default), the TTL 60 s (the
note), `lua-health-checks-expire-delay=86400` (the note). The web node
that is the primary answers `200` with the body `keel-primary
fd00:db8::ffff:1`. The other node answers `404` with the body
`replica`.

### How the times were measured

- A probe on the client asked each of the 3 servers for `www` A and
  AAAA about every 0.7 s, with no recursion. All CTs use the clock of
  the VM kernel.
- The test script wrote the time of each act. An act took 1.8 s to
  2.5 s to apply (an nginx reload through `pct exec`), 4.1 s to 5.3 s
  for `systemctl stop nginx`, and 4.0 s to 5.6 s for `pct stop`. The
  times below start at the start of the act.
- The pdns log (loglevel 6) has one line for each check result:
  "Lua record monitoring declaring <address> DOWN|UP". The nginx
  access logs show each check request.
- In each failover act, web-b changes to `200` at the same time as
  web-a fails. This is the pair that moves its primary. Both addresses
  are IPv4 and IPv6 (ULA) on the VM network. Both families were tested
  in each run.

### Measured times

The change happens during the act: nginx stops, or the file and the
reload apply, before the act command returns. Thus the time from the
start of the act is an upper bound. The time from the end of the act is
a lower bound. The script wrote the end of the act in 24 of the
32 switches.

| Case (runs) | New primary only, from the start of the act | From the end of the act | Both addresses from (start) |
| --- | --- | --- | --- |
| web-a nginx stopped, web-b 200 (6) | 8.3 s to 12.5 s | 6.2 s to 7.2 s (3 runs) | 4.8 s to 7.6 s |
| web-a powered off (`pct stop`), web-b 200 (3) | 14.2 s to 18.9 s | 9.7 s to 13.9 s | 2.9 s to 7.1 s |
| web-a 404, web-b 200 (6) | 8.3 s to 13.7 s | 6.3 s to 11.7 s (5 runs) | 3.5 s to 7.7 s |
| fail-back: web-b 404, web-a 200 (15) | 7.6 s to 14.4 s | 5.5 s to 12.4 s (11 runs) | 2.7 s to 7.9 s |
| web-a back as replica (404) while web-b is primary (6) | no change: web-b only at each answer | | none |

Each value is the later of A and AAAA on each of the 3 servers. The
rows hold runs with the default caches, 4 runs after a restart of all 3
servers, and 2 runs with `cache-ttl=0` and `query-cache-ttl=0`. The
runs with the caches off gave 7.7 s to 11.9 s from the start of the
act, in the same range. This agrees with the packet cache counters of
Q2: LUA answers are not cached.

**Each step of a switch** (from the pdns logs and the probe):

1. The act applies the change. In this test: 1.8 s to 5.6 s, as above.
   On a real pair this is the time until the pair moves (0045 section
   10 J).
2. The next check of each server comes 0 s to 5 s later. The servers
   check at different times. The first failed check of web-a came 3.2 s
   to 8.6 s after the start of the act.
3. **The first failed check does not mark web-a down**
   (`minimumFailures=2`). The first good check of web-b marks web-b up
   at once. From this check, the server gives both addresses.
4. **The second failed check marks web-a down.** It came 5.0 s after the
   first when web-a refused the connection or answered 404. It came
   10.0 s after the first when web-a was powered off (a timeout).
5. The answer changed in less than 0.7 s after the check that decided
   (the step of the probe). The packet cache adds no time, because it
   does not keep LUA answers (Q2).

The resolver cache (TTL 60 s) and the client cache come after these
steps. This test did not measure them.

**Why a timeout doubles the interval** (read in `pdns/lua-record.cc` at
5.1.5, `checkThread()`). The next check of an address is due at
`lastStatusUpdate + interval`. `lastStatusUpdate` is the time when the
check ended. A check that waits for the 2 s timeout ends 2 s after
the round starts. The next round, 5 s later, is "too early" for it, so
the check runs every 10 s. `lastStatusUpdate` is in whole seconds. Thus the same skip happens to
a fast check if the round starts a few ms before a whole second. In the
nginx logs of all runs, fast checks have a 5.0 s period. The exception
is dns3 in 2 runs. Its round started at a whole second, and 31 of its
intervals were 10 s. These 2 runs gave the 13.7 s and the 14.4 s.

### When all addresses fail

The times start at the start of the act.

- **web-a stopped and web-b 404 (1 run):** after 7.7 s to 12.0 s, every
  server gave both addresses (`backupSelector='all'`). When web-a came
  back, the servers gave web-a only after 5.0 s to 7.1 s.
- **web-a answers 200 with a wrong body (`maintenance`), web-b 404 (1
  run):** `stringmatch` marked web-a down. After 8.1 s to 10.3 s,
  every server gave both addresses.
- **A DNS server that cannot reach web-a and web-b** (routes `prohibit`,
  then `blackhole`, inside dns3): dns3 gave both addresses for A and
  AAAA after its checks failed, in both modes. dns2, which still
  reached the nodes, gave web-a only.

### A server that starts

dns3 restarted with `systemctl restart pdns`, and the client asked
`www` about every 0.3 s on the loopback. The times are from the end of
the restart command.

| Case | Query 1 | Next queries | First correct answer |
| --- | --- | --- | --- |
| i: web-a 200, web-b 404, A | SERVFAIL at 1.9 s | both addresses | 7.1 s |
| i: the same, AAAA | SERVFAIL at 0.2 s | both addresses | 5.3 s |
| ii: web-a 503, web-b 200 | SERVFAIL at 0.2 s | both addresses | 5.2 s |
| iii: web-a refuses, web-b 200 | SERVFAIL at 0.2 s | both addresses | 5.3 s |

The pdns log shows why. The first check of each address came within
0.1 s of the first query. web-a (200) was up at once. web-b (404) had
1 failure, which with `minimumFailures=2` still counts as up. Its
second failure, 5 s later, marked it down. Thus:

- `failOnIncompleteCheck` gives SERVFAIL only to the query that makes
  the check. The code (`IsUpOracle::isUp`) returns "incomplete" only
  when it inserts the check. Later queries before the first result see
  "all down", and `backupSelector='all'` gives both addresses.
- The first failed check of an address counts as up
  (`state->status = ++state->failures < minimumFailures`).
- A cold server gives both addresses for about 5 s. One more interval
  is added if an address times out.

**DNSSEC from a cold server** (dns2 restarted, `delv` as the first
query): the first `delv` gave "resolution failed: failure" (the
SERVFAIL). The second, 1 s later, gave "fully validated" with both
addresses. The third, 12 s later, gave "fully validated" with web-a
only.

### Redirects

`minicurl.cc` at 5.1.5 sets `CURLOPT_FOLLOWLOCATION`. The test record
`redir.example.test` lists web-a and web-b. On web-a, the name answers
`301`. web-b answers 404 on the check path and `200` with the match
string on `/redirect-target`.

- **301 to `https://<web-b IPv4>/redirect-target`:** each server
  followed the redirect. web-b logged the requests from the 3 servers
  (`host=<web-b IPv4>`, no SNI). The check of web-a passed with the
  answer of web-b. All 3 servers gave web-a only, but web-a did not
  serve the primary answer.
- **301 to `https://other.example.test/redirect-target`, with the name
  in `/etc/hosts` of dns3 only:** dns3 followed it (web-b logged
  `sni=other.example.test`) and gave web-a only. dns1 and dns2 logged
  "Unable to retrieve URL (301): Could not resolve hostname" and gave
  both addresses. The check resolves a redirect target with the DNS
  server's own resolver.

### IPv4 and IPv6

Each run moved the A record and the AAAA record. Both families moved
with the same steps. The difference between A and AAAA of one server
was at most 1 check interval. The IPv6 tests used the ULA prefix of the
VLAN. The public IPv6 prefix of the VLAN was not used.

## Q4: the check through a TCP proxy that routes by SNI

The proxy CT runs HAProxy in `mode tcp`. It listens on its IPv4 and its
ULA address on 443. `req_ssl_sni -i www.example.test` goes to web-a,
and `req_ssl_sni -i other.example.test` goes to web-b. The back ends
are IPv4. `timeout connect 5s`, with the default retries. TLS ends on
the web nodes (self-signed). The record:

```
edge.example.test. 60 IN LUA A "ifurlup('https://www.example.test/.well-known/keel/primary', {'<proxy IPv4>', '<web-b IPv4>'}, {...the options of Q3...})"
```

with the same AAAA record on the ULA addresses.

- **SNI routing.** The HAProxy log has 1530 connections with the SNI
  `www.example.test` to `node_a`, and the 1 test connection with
  `other.example.test` to `node_b`. The check of `edge` sends the host
  of the URL as SNI and reaches web-a through the proxy.
- **The check reads the node's answer.** When web-a answered 200, the
  proxy address was up and `edge` gave the proxy only. When web-a
  answered 404, the pdns log gave "declaring <proxy> DOWN ... (404)".
- **The proxy is up and web-a is down.** With nginx stopped on web-a,
  HAProxy retried the connection for 3 s (log `SC`, `-1/3007`). With
  web-a powered off, HAProxy waited 20 s (log `sC`). In both cases the
  check stopped at its 2 s timeout: "Unable to retrieve URL (0):
  Timeout was reached". The proxy address was marked down, and `edge`
  gave both addresses (web-b was 404 in this case).
- Because the check through the proxy is a timeout, it has the 10 s
  period of Q3, step 4.

## Sentences of 0045 that the results confirm or contradict

This section quotes the note at handbook#201, commit `90205c1`. The note
is not changed here. Where a result contradicted an older text of the
note, and the note now gives the measured value, this section says "the
note was corrected".

**Confirmed:**

- Section 3: "A PowerDNS server only requires database write access if
  it is participating as a primary or secondary in zone transfers, or
  has a frontend attached for managing records". Both standbys served
  all zones read-only.
- Section 3: a standby runs with "no `pdnsutil` act that writes". Both
  write acts that this test made on purpose failed on the standby with
  "read-only transaction".
- Section 3: a standby runs with "`primary=no` and `secondary=no`" and
  "`api=no`". These were enough. No query path wrote.
- Section 3, the table of ways: "each standby answers and signs from its
  local copy". True when the writer stopped for 120 s, and when a
  standby lost the replication for 180 s.
- Section 7: "`enable-lua-records=yes` on each server, in the file."
- Section 10 A: the check address answers 200 "with the body
  `keel-primary <token>`", and "An error page, a maintenance page or a
  cache must never hold the token". With `stringmatch`, a 200 with a
  wrong body counted as down.
- Section 10 A: "Thus the check connects to the listed address, sends
  the host of the URL as SNI and as `Host`, and does not verify the
  certificate." Self-signed certificates passed, and the proxy routed
  the check by the SNI of the URL.
- Section 10 A: "If an edge stays up and the node behind it is the
  replica, the check gets 503 from the replica, and the name leaves that
  address." True with a 404 through the proxy.
- Section 10 B, the table: two servers "can disagree" "for one check
  interval". The 3 servers differed by up to 5 s.
- Section 10 H, item 2: "The check reaches the node that the edge gives
  for the name. The edge does not see the path. This works with no
  change to the edge." True for a TCP proxy that routes by SNI, in the
  laboratory.
- Section 10 H, item 4: "A TCP open on 443 of an edge proves only the
  edge." The proxy accepted TCP while the node behind it was down.

**Contradicted, and the note was corrected:**

- An older text said that the build of the Debian source 5.1.5-2 on
  trixie was not verified. It builds with no change (Q1). Section 1 now
  gives the result.
- An older text gave `api-readonly=yes` as an option. It does not exist
  in 5.1.5, and a file with it stops `pdns` at start. Section 3 now
  gives only `api=no`.
- An older text said that a server with no check result yet answers
  SERVFAIL. Only the query that makes the check gets SERVFAIL. The next
  queries find all addresses down: with `backupSelector='all'` they got
  both addresses for about 5 s. Section 7 now states this.
- An older text estimated that each DNS server sees the new primary
  within one check interval and the timeout (7 s). Measured, as lower
  and upper bound: 5.5 s to 14.4 s when the old primary refuses or
  answers 404, and 9.7 s to 18.9 s when it is powered off. With
  `minimumFailures=2`, 2 failed checks are necessary, and a check that
  times out runs every 10 s. Section 10 J now gives these values.
- An older text said that a change on the writer reaches each standby
  within 60 s. True for a record change (16.6 s to 22.1 s). Not true
  for a new zone: each server, the writer too, serves a new zone only at
  its next zone cache refresh (up to 300 s), or after `pdns_control
  rediscover`. Section 4 now states this.
- An older text said that the real test checks if `pdnsutil` needs
  `enable-lua-record-updates`. It does not. Section 7 now states this.

**Measured here, and now in the note:**

- `minimumFailures=2`: the first failed check counts as up. In each
  switch and after each start, every server gives both addresses for
  about 5 s (10 s for a timeout). Section 7 keeps the value 1, which
  this test did not run.
- `ifurlup` follows redirects. A check URL that answers 3xx can pass on
  the answer of another host. The DNS server resolves the target name
  with its own resolver. Section 10 A says that the check address must
  not redirect.
- The packet cache does not keep LUA answers (section 7, section 10 J).
- A LUA record at the zone apex works, for A and AAAA, signed (section
  10 E).
- A `pdns.conf` that replaces the Debian file must keep
  `include-dir=/etc/powerdns/pdns.d` (section 3).
- A PostgreSQL `listen_addresses` with fixed addresses fails to bind if
  PostgreSQL starts before the addresses exist (section 3).

**Not tested here:** the choice of section 7 for the case where no
address is up (`backupSelector='empty'` and a Lua error, so SERVFAIL),
and `minimumFailures=1`. This test ran only `backupSelector='all'` and
`minimumFailures=2`.

## What failed or went wrong in the test

- `dscverify` failed: the signing key of the upload is not in the
  `debian-keyring` package of trixie. apt checked the source against
  the archive index.
- The first build ran with 2 jobs and was stopped at step 12 of 290.
  The second build, with 4 jobs, is the result.
- The first `pdns.conf` had no `include-dir`. The first pass of the
  conflict test, of the `cache-ttl=0` runs and of `api-readonly` in a
  file thus ran with the defaults. Their results are kept with the
  label "caches on" and are not used for the statements above that
  need the setting.
- PostgreSQL on the writer did not bind its addresses after a restart
  of the CT (Q2).
- The `pg_stat_database_conflicts` reads of the first 2 conflict runs
  failed (file permission). The counters are cumulative, and later
  reads show 0.

## What was not tested

- A resolver, netem (250 ms, 2 % loss) and the client caches. The
  times above end at the answer of the DNS server.
- A real Keel pair, the address `/.well-known/keel/primary` of keel,
  `cloud_advanced`, and the etcd witness. web-a and web-b are plain
  nginx with a fixed answer.
- TLS on the PostgreSQL replication, and replication over a real link
  between sites.
- The public IPv6 prefix and public IPv4. All addresses were private
  (the VLAN /24 and its ULA /64).
- The Keel `postgresql` image.
- A ZSK roll or a KSK roll with waits, a standby that lags during a
  roll, and the import of keys from another server.
- TLS that ends on the proxy (0045 section 10 H, outside version 1),
  and an active and a standby proxy.
- `ifurlup` with a per-check `interval`, or a TTL other than 60 s.
- An outside AXFR secondary.
