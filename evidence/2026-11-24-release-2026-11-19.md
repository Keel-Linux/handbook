```
nc-flat-548e8cd:    core 46cf47af… web ab715859… lnmp 92608e24… nextcloud 5ea0dab6…: fetched; layers: 4 checked, 4 ok
```

Why keel 0.23.97 cannot pull this release:

- `--release R --rev N` verifies the signed `revision` file in
  `layers/R/N/`. The mirror writes that file only when a channel pointer
  names `R/N` (`lib/mirror.sh`, the channel script). This release was
  published with `--no-channels`, so the file does not exist.
- The flat layout reads the plain parent names. The nextcloud layer names
  its parent lnmp by sha256 (`92608e24…`). The plain `lnmp` name stays on
  the published lnmp layer (`7151751f…`) that the other applications use.
  keel 0.23.98 finds a parent by its sha256 name; keel 0.23.97 does not.

**The command list was wrong.** Step 7 expected that keel 0.23.97 pulls
nextcloud with `--release 2026-11-19 --rev 1`, and its follow-up note said
the same. That expectation did not include the rule above about the
`revision` file. The check stopped the procedure before step 8. The
maintainer then accepted, for this release, the expectation "a flat
`keel pull nextcloud` with keel 0.23.98 or later passes". That check had
passed already. Nothing more was signed, and no `revision` file was
written.

## keel-nextcloud

From the publication until the merge of keel-nextcloud#6, the gate of
keel-nextcloud main was red: the gate refuses the exemption for an
unpublished layer when the layer is published. keel-nextcloud#6 removes the
exemption, so the gate boots the published layer.

The first CI run of keel-nextcloud#6 (run 16) pulled and verified the
published chain, then failed: `tests/boot-test.sh is missing or not
executable in this repository`. keel-nextcloud never had a boot test. The
maintainer chose to add one on the same branch (commit fc54308, `test:`).
