## MariaDB pair (9053 BR1 + 9061 BR2) — PASS

Flow (keel CLI): mesh create -> invite -> join -> sync -> vip pair (both)
-> spec apply --system-only (primary, then replica) -> vip promote
-> database status -> write/read -> database promote (failover)
-> old primary rejoins by itself.

### Trap found and recovered (documented for the maintainer)

`keel mesh create` makes the mesh's root CA only when
`installation.mode: cloud_simple` (or cloud_advanced) is declared in the
spec (keel maintainer decision 2026-10-11: "the root is made in every
cloud mode"; dbtls.py: "a cloud simple pair, whose first node made the
root at keel mesh create"). Our first create ran with the mode undeclared
(simple): the pair formed but the database certificate could not be made —
BR1 asked BR2 (its stale holder view), BR2 refused "this node does not
hold the mesh's root CA". Recovery without rebuild: declared
`installation.mode: cloud_simple` on both nodes, then invoked the shipped
code path `etcd.created()` on BR1 (the same call create.py makes);
`keel mesh sync` on BR2 fetched the root anchor + holder notice from the
roster (keel#105 mechanism).

Also: `database.server` apply REFUSES before `keel vip pair` ("run keel
vip pair with the other node's overlay address on one node of the pair,
then apply again") — the order mesh -> pair -> apply is enforced.

## PostgreSQL pair (9054 BR1 + 9062 BR2) — cloud functions PASS, database.server not in this version

### Finding: the step-12 postgresql and redis images ship no appliance manifest

`/usr/share/keel/appliances/` on 9054/9055 (and the 9062/9063 BR2 CTs, and
the shipped tarballs debian-13-keel-postgresql_19.0-6 / _redis_19.0-9)
contains only `core.yaml`. The mariadb image additionally ships the
`keel-mariadb` 0.1.1 package, which provides `mariadb.yaml`
(`dpkg -S /usr/share/keel/appliances/mariadb.yaml` on 9053). No
`keel-postgresql`/`keel-redis` manifest package exists locally: none of
`repos/keel-{mariadb,postgresql,redis}/plan/main` name one, none of the
repos carry a manifest yaml or `debian/` packaging, and `repos/keel/debian`
builds only the `keel` package.

Consequence: on a pristine postgresql/redis appliance the spec cannot
declare `appliance.name` at all — validate rejects it ("not an installed
appliance under /usr/share/keel"), and without `appliance.vip` the
`keel vip pair` step refuses ("this node declares no appliance.vip: there
is no pair to record"). The VIP/pair flow is unreachable on these images.

Harness stand-in (test-only, documented here): a minimal manifest
`postgresql.yaml` / `redis.yaml` (shape mirroring mariadb.yaml, summary
line inside the file says HARNESS STAND-IN, not a product artefact) was
written on the four test CTs, and the specs declare appliance.name/vip.
Everything below ran with that stand-in; nothing product-side was built
or patched.

Second finding (pre-existing, by design, NOT a step-12 regression): even
with a manifest, master/slave for these engines is not implemented in
keel 0.23.13. `database.server` converge is MariaDB-only
(`keel/system/database.py`: dbmariadb, dbseed, dbfollow, dbtls, dbstatus;
no postgres/redis module). The shipped answer, captured live on the CTs:

```
database.server: postgresql is read by keel inspect and compared by keel
diff, and its roles are not configured by this version; decision 0013
takes the engines one at a time and MariaDB is the first
database.server: redis is read by keel inspect and compared by keel diff,
... (identical wording)
```

So the engine-independent cloud functions (mesh, VIP pair/promote/failover)
were exercised per engine; database master/slave over the mesh is
MariaDB-only in this version, matching decision 0013's staged plan.

### Operability note from the redis run (harness-induced, one product
### observation)

A first join attempt on 9063 was interrupted mid-flight (harness ssh
timeout, not a product fault). The designed recovery worked: the network
window reverted wg0 by itself and `keel network revert` removed the
leftover pending change ("removed /etc/wireguard/wg0.conf, which the
change had created"). One stale artefact needed a manual kick: the
transient `keel-mesh-members-listen` unit from the interrupted join
stayed `active (running)` but held a dead socket, so `keel mesh sync`
from the peer failed with "[...]:51821 through wg0: Connection refused"
until `systemctl restart keel-mesh-members-listen`. A join that never
completes could leave the members' channel deaf on that node until the
unit is restarted — worth a look in the product (self-heal or rebind on
the members channel).

Product gaps found (both pre-existing, not step-12 regressions):
1. postgresql and redis images ship no appliance manifest, so
   `appliance.name`/`appliance.vip` cannot be declared on a pristine
   image and the VIP/pair flow is unreachable for them.
2. `database.server` converge is MariaDB-only in 0.23.13 (decision 0013
   staged engines); pg/redis are inspect/diff-only.
3. Minor: a never-completed join can leave the members-listen unit
   active-but-deaf until restarted.
