### How the release directory holds 11 layers

The release tool does not make a cumulative release. To keep the 8 layers
of release 2026-11-10 on the channel, the operator did these steps on the
build host. This is a workaround, not an approved procedure (see
"Follow-ups").

1. The operator copied by hand the 6 layer sets of release 2026-11-10
   that this release does not build again into
   `/srv/keel-release/2026-11-11`, with `cp -p --no-clobber`. This was 32
   files.
2. The operator compared each copied file with the MANIFEST of release
   2026-11-10. Each file was byte-equal.
3. The operator ran `keel verify --layers-dir` on the new directory. The
   result was 11 ok.
4. The operator ran
   `keel-release --sign-only --date 2026-11-11 mariadb redis ntfy`.

No step wrote to the directory of release 2026-11-10. The fingerprint of
its MANIFEST did not change.

The two failures are a fault of the test container, not of the release.
On BR1 the container is on the bridge vtnet88 with tag 5. A new container
there gets only an IPv6 SLAAC address and no IPv4 address from DHCP.
Proxmox VE copies the resolver of the host, `nameserver 1.1.1.1`, into the
container. That resolver has only an IPv4 address and the container has
no IPv4 address, so the container cannot resolve names.
The correction is `--nameserver 2606:4700:4700::1111` on `pct create`.
