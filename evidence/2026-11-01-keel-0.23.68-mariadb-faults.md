# keel 0.23.68 and keel-mariadb 0.1.1: failure modes of a MariaDB pair

Date: 2026-11-01. The time zone is UTC. No secret is in this file.

This test continues `evidence/2026-11-01-keel-0.23.68-mariadb-real.md`, on the
same CTs. It did not promote a package and it did not change the product.

## Result

**0 of 29627 writes that the writer counted were lost in the failure cases.
Two defects need a decision before promotion. A separate case, made to measure
the fallback, lost 60 of 60 acknowledged writes, and keel reported no drift.**

| Finding | Severity | Status |
| --- | --- | --- |
| 1. A replica that is away, or behind, can become the primary without acknowledged writes. In case F2, 60 of 60 were absent from the new primary. | High. The docs tell that a failover loses these writes. | Designed loss, with finding 2 |
| 2. During the fallback, `keel diff` says `semi_sync: same (on)` and `no drift`, and `keel database watch` sends no alert. The docs tell that it reports drift. | High | keel#107. The fix is in PR `fix/semi-sync-no-replica`, not in 0.23.68. This test did not run that fix. |
| 3. A primary with a large backlog: 116 minutes with no writes, after one failure, with no acknowledged write lost. | High for availability | New |
| 4. A diverged node writes a new dump each 30 s with no limit: 223 files, 246 MB after about 2.5 hours. In a long divergence this fills the disk. | Medium | New |
| 5. `docs/replication.md` describes `keel database dump` and `keel-database-dump.timer`. keel 0.23.68 has neither one. A pair has no scheduled backup. | Medium | New |
| 6. A full disk on the primary stops the writes for as long as the disk is full. The VIP does not move. | Medium | New, to decide |
| 7. "This node holds 1 transaction(s)" was shown when the node held about 13000 that the holder lacked. | Low | New |
| 8. `keel spec apply --system-only` says 3 changes at each run on a pair node. | Low | The server PID and the epoch do not change. |

In 3310 samples at about 1 s to 3 s intervals, both nodes were never writable
at the same time. A shorter overlap than the sample time is not excluded.

## Setup

CTs 9320 (W, etcd member and writer), 9321 (B) and 9322 (C), keel 0.23.68,
keel-mariadb 0.1.1, etcd of 3, VIP `fd6e:ab4a:ac10::ffff:1`. The normal link is
netem on the host side of C's veth: `delay 250ms 25ms loss 1.5%`.

The writer on W is the one of the earlier test: one row at a time through the
VIP, 0.1 s between writes, connect timeout 3 s, `timeout 15`. An id counts only
if the client returned 0. A sampler read `read_only` on B and C through
`pct exec`, so it worked during a cut. A cut is netem `loss 100%` on the veth.

The "Ack gap" is the longest time with no acknowledged write in the case.

### The fallback (F1): what it gives

C was cut, with holder B and the writer stopped. Four timed inserts:

```
fallback insert 1 took 15.07 s
fallback insert 2 took 0.08 s
fallback insert 3 took 0.10 s
fallback insert 4 took 0.08 s
Rpl_semi_sync_master_status ON, Rpl_semi_sync_master_clients 0, no_tx rising
database.server.semi_sync: same (on)
diff: 39 same, 0 drift ... no drift, exit 0
database watch: role primary, semi-synchronous on (was on)
```

- **The stall was 15 s, not 30 s.** The dump thread to the replica ended first
  (docs: about 12.6 s with `tcp_retries2 = 5`), and with `wait_no_slave = OFF` a
  commit with no replica connected is acknowledged at once. This test did not
  measure the 30 s timeout itself. It needs a replica that stays connected and
  sends no acknowledgement.
- **The status stays `ON`.** `Rpl_semi_sync_master_status` is not the signal
  of this state. The signal is `Rpl_semi_sync_master_clients` 0.

**The durability, exactly.** With the replica connected and caught up, an
acknowledged write is on 2 nodes. From the moment the replica is gone or
behind, an acknowledged write is on 1 node only, until the replica catches up.
If that node is lost in this time, the writes are not on the new primary. They
are in the old primary's data, and in its dump, if that node comes back.

### The loss (F2)

The two nodes had the same GTID. C was cut. 60 rows were written, and 60 were
acknowledged. `keel diff` on B said `no drift`. B was then cut and C healed in
the same second, which is a primary that dies while its replica is away.

```
keel database status: 0 replica(s) acknowledging, 101 commits acknowledged, 77 not
fb rows on B=60
new primary C writable at +24.6 s, epoch 34
C has fb rows=0 of 60 acked
```

After the heal, B stayed read only and diverged, and `keel diff` reported
`database.server.diverged`. The 60 rows are in each dump of B under
`/var/backups/keel/mariadb/`. Nothing puts them back by itself. The reseed
`keel spec apply --system-only --destroy-local-database` passed: B became a
replica of C, the pair was ready 14 s after the writer restarted, and no other
acknowledged id was missing. The 60 rows are not in the accounting above.

### The long absence (G) and the outage (K1)

C was cut for 660 s under the writer and a bulk load of 500 rows of 1 KB each
2 s. At the end of the cut there were 156500 bulk rows. After the heal,
`Seconds_Behind_Master` said 0, but C was far behind: 914 s later, C had 13359
rows of `t` and B had 21732. **`Seconds_Behind_Master` is not a usable sign of
catch-up here, and neither was the check of this test.** The test then stopped
the bulk load and continued with the writer.

The full catch-up ended at about 09:49, about 147 minutes after the heal. This
is about 2 transactions per second, or some tens of KB/s. The test did not
measure the link bandwidth, so the cause is not proven. The likely limit is TCP
over 250 ms with 1.5 % loss.

The first rapid round (K1) ran while C was still behind, because the readiness
check of the test did not compare the GTID. It shows what a lagging replica does:

```
07:53:36 B killed and cut, B at about sequence 27978, C at about 14600
07:54:01 C: claimed at epoch 22
08:04:03 C: refused: the SQL thread did not apply everything it had received within 600 s
07:55:53 B (healed 07:55:39): refused: diverged: this node holds 1 transaction(s)
08:05:49 C: drained and promoted: this node replicates from nobody and takes writes
08:05:50 C: set read_only ON (the test had cut C again at 08:05:36)
08:07:50 C: rejoined: no errant GTID, replicating from B from 0-1628676891-14614
09:48:55 B: rejoined, no errant GTID
09:49:35 B: claimed at epoch 23
```

- No write was accepted from 07:53 to 09:49: the gap was 6960 s.
- **The test did not show the end of this path with no second cut.** C was
  promoted at about sequence 14614 while B held 27978. C was read only again 1 s
  later only because the second round of the test had cut it. With no such cut,
  the likely result is F2 at a larger scale: about 13000 acknowledged writes
  absent from a writable primary.
- Rounds 2 to 10 of K1 are not valid. Round 2 cut the node that was being
  promoted, and from round 3 no node held the VIP, so the rounds did nothing.

### Idempotence (L)

After all of the above, `keel spec apply --system-only` ran 2 times on each node
with the writer on:

```
W: 0 change(s), 0 failed. B and C: 3 change(s), 0 failed, at each run
before: B=309925 C=211098 epoch 35; after: B=309925 C=211098 epoch 35
keel diff: 0 drift, exit 0 on W, B and C
```

The 3 changes are the database certificate, the replication authorization and
the role follow, which run at each apply. The server was not restarted.

### Backup and restore

The docs describe a daily dump on the replica, but the command and the timer do
not exist in 0.23.68 (finding 5), and they describe no restore procedure. The
test restored what exists: a rejoin dump of C into a temporary server on W, with
its own data directory.

```
restored: 29174 rows in pairtest.t below id 9000000, max id 33915
```

This shows that the dump can be read and loaded. It does not show a restore of a
pair. The reseed in F2 is the only tested path that makes a node whole again.

## What went wrong in the test

These are errors of the test, not defects of the product.

- **E1 did not lose quorum.** C's etcd stayed `deactivating`, because the unit
  has `ExecStop=keel mesh etcd gate stop`, which holds a stop while W is down. So
  the holder kept writing, correctly. E1b killed the processes.
- **The K1 readiness check did not compare the GTID,** so K1 ran on a lagging
  replica and its rounds 2 to 10 are not valid. K2 is the valid set.
- **A `pkill -f` matched the shell that ran it** and ended that command. No CT
  was affected.
- **The first log of each helper named the wrong holder** (a shell variable
  overwritten). The checks had the right node. It is corrected.
- **The test account had no right on the bulk table.** The test added it before
  case G.
- **The first restore failed:** `mysql` could not enter `/root`. It ran again
  under `/var/tmp`.
- **A wrong edit put a file that does not exist into `/root/writer.sh`.** The
  running writer was not affected, and the edit is removed.
- **The copy of the F2 dumps was deleted, and a first check with a wrong pattern
  said 0.** The same dumps under `/var/backups/keel/mariadb/` were read again with
  a corrected pattern, and they hold the 60 rows.
- **A 10-minute timeout of the waiting tool** moved some waits to the background.
  It changed no case.

## What this test does not show

- keel 0.23.68 only. It does not have the open PRs, and keel#107 in particular.
- A live pair that upgrades from 0.23.62. This test did not do it.
- WordPress on the pair.
- BR3-THIN. The etcd members are 2 on BR1 and 1 on BR2, so a cut of BR2 never
  cuts the majority from the holder's site.
- A cut of BR1 as a site. W and B cannot be cut from C with their link to each
  other kept, with netem on the veth only.
- An alert. No channel was set (`/etc/keel/monitor.json: secret file not found`),
  so the test read the journal lines, not a delivered alert.
- The size limits of a real disk. The disk cases were short.

## State left

CTs 9320, 9321 and 9322 run. B holds the VIP at epoch 35, and C replicates with
the same GTID. Netem stays on C's veth, and the veths of W and B have none. The
ZFS quota of C is 8G again. The writer is stopped, `/root/.my.cnf` is removed
from W, and the local test password is deleted. In the test database, the
account `pt` and the tables `t` and `bulk` remain. B and C still hold the rejoin
dumps under `/var/backups/keel/mariadb/` (223 files on B).
