# OJS 3.5 on the Keel LNMP image: the first test by hand

Date: 2026-11-10

This file is the evidence for the places marked "(first test)" in
decision note 0084 (proposed). It is a test by hand. No package was
built. It is not a commissioning test (0075).

## The question

Does OJS 3.5 run on PHP 8.4 and MariaDB 11.8 of Debian 13? Does an
upgrade of one build to the next build work with a code tree and a
`config.inc.php` that the web user cannot write (the layout of note
0084, section 4)?

Added to the image for the test:
- From Debian: `php8.4-bcmath`, `php8.4-curl`, `php8.4-gd`,
  `php8.4-intl`, `php8.4-mbstring`, `php8.4-xml`, `php8.4-zip`. OJS
  needs them and LNMP does not have them. For the measurements only:
  `strace` and `libfcgi-bin`.
- A PHP-FPM pool setting `error_reporting = E_ALL` with the error log
  on, an nginx site for OJS in place of the default site, and a host
  name in `/etc/hosts`.

The layout was that of note 0084: the code in `/usr/share/ojs` owned by
root, links for `config.inc.php` (to `/etc/ojs`, root:www-data 0640),
`cache` and `public`, and `files_dir` in `/var/lib/ojs/files`.

### The install

```
config before: root:www-data 640 app_key sha256=2cae0de4cf15 installed=installed = Off
rc=0 duration=85s
Successfully installed version 3.5.0.5
```

The installer could not write the config, so it printed the file that
it wanted to write. The differences from the file in place:

```
app_key: DIFFERS (value hidden)
installed: file=[installed = Off] installer=[installed = On]
allowed_hosts: file=[allowed_hosts = '["[...]", "localhost", "127.0.0.1"]'] installer=[allowed_hosts = "[\"\"]"]
time_zone: file=[time_zone = "UTC"] installer=[time_zone = ]
enable_beacon: file=[enable_beacon = On] installer=[enable_beacon = Off]
```

Thus the installer makes its own `app_key`, and with a writable file it
replaces the key that was there. After the install, root set
`installed = On`.

With `base_url` as an IPv6 address in brackets, the session cookie got
that text as its domain, curl did not keep the cookie, and the login
failed. The test then used a host name.

### After the upgrade

- The first requests after the upgrade were made with a PHP-FPM that
  was not restarted (started 18:12:25 UTC, before the change of the
  code). They were made at 18:19:19 UTC, less than 60 seconds after the
  change of the code, and they showed 3.5.0.6. `revalidate_freq` is 30,
  so old code for up to 30 seconds is possible. The test did not see it
  and did not measure it.
- Then PHP-FPM was restarted and the template cache was cleared, and
  the page check ran. After it, OPcache held 1086 scripts. The code has
  its keys under `/usr/share/ojs/`, and the 7 compiled templates have
  theirs under `/var/cache/ojs/t_compile/`.
- www-data cannot write the code tree or the config:

```
touch: cannot touch '/usr/share/ojs/x': Permission denied
touch: cannot touch '/usr/share/ojs/plugins/generic/x': Permission denied
touch: cannot touch '/usr/share/ojs/lib/pkp/x': Permission denied
sh: 1: cannot create /etc/ojs/config.inc.php: Permission denied
```

- `PluginHelper::installPlugin()`, the function of the plugin upload
  form, refuses: "Failed to copy plugin to destination folder". It made
  no directory and no `versions` row. It was called from the command
  line, not through the form.

### The deprecation messages on PHP 8.4 (3.5.0-6)

- `xml_set_object()`, `xml_set_element_handler()` and
  `xml_set_character_data_handler()` in `PKPXMLParser.php`.
- "Implicitly marking parameter as nullable" in some classes and in
  `less.php`.
- "Optional parameter declared before required" in the email template
  classes.
- `null` given to `str_replace` or `substr` in the login, registration
  and search handlers.
- Smarty: a static method that a template uses and that is not
  registered (8 different messages).

They are messages, not failures. A later PHP can make some of them
errors.

## What this does not show

- A new install of 3.5.0-6. The test installed 3.5.0-5 and upgraded it.
- The PKP checklist of the upgrade guide (step 11).
- The cause of the `TypeError` on 3.5.0-5: PHP 8.4, or the ICU library
  of trixie. It agrees with pkp-lib issues 13139 and 13140.
- An upgrade from 3.3 or 3.4, a large journal, a migration that fails,
  and the restore.
- The 503 maintenance mark, `jobs.php restart`, the worker and the
  scheduler.
- `plugin_gallery_urls`, `installPluginVersion.php`, a plugin package
  and a local plugin directory.
- A pair, Syncthing, and a slow link (netem).
- A browser. All requests were made with curl.
- How much of the 85 seconds of the install is a download. The first
  boot needs the network for the install; the part was not measured.

## State after the test

CT 9364 is stopped and not removed. Nothing was published. The command
logs of the test are with the coordinator; this file holds the lines
that the note uses.
