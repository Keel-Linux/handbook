# OJS 3.3 to 3.5 on the Keel LNMP image: the upgrade, an interrupted upgrade and the restore

Date: 2026-11-10

This file is the evidence for the places marked "(third test)" in
decision note 0084. It covers tests 3 and 4 of that note, and one part
of test 5. It is a test by hand. No package was built. It is not a
commissioning test (0075).

## The question

1. Does the upgrade of a 3.3.0-24 database to 3.5.0-6 pass on MariaDB
   11.8 and PHP 8.4, with a code tree and a `config.inc.php` that the
   web user cannot write?
2. What state does an interrupted upgrade leave?
3. Does the restore of note 0084, section 7, give back the state before
   the upgrade?

### Before the upgrade

With the 3.5.0-6 code on the 3.3 database, `upgrade.php check` said:
"Code version 3.5.0.6, Database version 3.3.0.24", and it asked for the
upgrade. Each page gave HTTP 500 with an empty body. The PHP error is a
`PDOException`, "Unknown column 'id' in 'WHERE'", from the session
code.

### The pre-flight check and `base_url`

The first run stopped at
`APP\migration\upgrade\v3_4_0\PreflightCheckMigration`:

```
label=A memory_limit=2048M strace rc=2 duration=2.6s
[A pre-flight check failed. The software was successfully upgraded to 3.3.9.9 but could not be upgraded further (to 3.5.0.6). Check and correct the error, then try again.]
ERROR: Upgrade failed: DB: The base_url in config.inc.php should be the same as in URLs in the usage stats log file.
```

After this run, `versions` has `3.3.0.24` with `current = 0` and
`3.3.9.9` with `current = 1`. The schema did not change (0 lines differ
in a schema dump). The test then set `base_url` to the URL of the
dataset (`http://localhost`), and the check passed.

### The upgrade

```
label=A memory_limit=2048M strace rc=0 duration=117.8s
Maximum resident set size (kbytes): 106884
Successfully upgraded to version 3.5.0.6
```

The run had 123 migrations and 5 code steps. The first 14 seconds were
schema and data migrations. The next 97 seconds were one migration,
`I7135_CreateNewRorRegistryCacheTables`, which downloads the ROR
registry. The download of the IP database of the usage statistics took
3 seconds. After the run, `rors` has 146,716 rows and the IP database
file has 126,873,350 bytes.

What the process wrote, from the `strace` record:

| Check | Result |
|---|---|
| sha256 of `/etc/ojs/config.inc.php` before and after | the same |
| Opens of `config.inc.php` | 1, with `O_RDONLY` |
| `EACCES` in the record | 0 |
| Files under `/usr/share/ojs` newer than the start of the run | 0 |
| Paths written | `/var/cache/ojs` (through the link), `/var/lib/ojs/files`, `/var/log/ojs` |

The command-line PHP log of the run: 0 errors, 55 deprecation messages,
58 notices "problem finding IP in the Geo database" for 127.0.0.1, and
3 warnings from the navigation menu step.

### After the upgrade

- `versions`: core 3.5.0.6 is current.
- The counts of journals, users, submissions, publications, submission
  files, issues and galleys are the same as before.
- Tables: 114 before, 136 after. 8 tables are gone and 30 are new.
- The public pages, the login, the dashboard and the pages of an editor
  and of the administrator give HTTP 200. The API gives the 19
  submissions and the 2 issues to an editor. An API request with no
  login gives HTTP 401, which is correct. A galley PDF has the same
  sha256 as before.
- The PHP-FPM log of the page check: 0 errors, 5 deprecation messages.
- 3 `issueId` rows left `publication_settings`. The value is now the
  column `publications.issue_id`.

### Collations

Each table of the dump has `DEFAULT CHARSET=utf8mb3` and no collation.
MariaDB 11.8 gave the 114 loaded tables `utf8mb3_uca1400_ai_ci`,
although the database was created with `utf8mb3_general_ci`. The
upgrade makes its tables with the default of the OJS database
connection (`utf8`, `utf8_general_ci` in
`lib/pkp/classes/core/PKPContainer.php`). After the upgrade, 105 tables
have `utf8mb3_uca1400_ai_ci`, and 31 tables have `utf8mb3_general_ci`:
the 30 new tables and `sessions`. The test found no error from this
mix. It did not test a join of text columns across the two groups.

### Plugins of 3.3 that 3.5 does not have

Before the upgrade, 10 plugin rows of `versions` with `current = 1`
have no directory in the 3.5.0-6 tree: `auth/ldap`,
`gateways/resolver`, `generic/usageStats`, `generic/orcidProfile`,
`generic/acron`, `importexport/crossref`, `importexport/datacite`,
`pubIds/doi`, `reports/counterReport` and `reports/views`. 3.3 bundles
all of them.

After the upgrade:
- 5 old rows stay with `current = 1` and the old date: `ldap`,
  `resolver`, `acron`, `orcidProfile` and `counterReport`.
- `crossref` and `datacite` have new rows under `plugins.generic`.
- `usageStats`, `doi` and `views` have no current row.

The upgrade passed with these rows. So a rule "each active plugin row
has a package" refuses each 3.3 import.

### `app_key`

The migration `I9895_AddAppKeyToConfigFile` writes `app_key` into the
config. With a config that www-data cannot write:

| Config before the upgrade | Upgrade | The log | Site after |
|---|---|---|---|
| `app_key` has a value | Code 0 | no message | HTTP 200 |
| `app_key =` with no value | Code 0, "Successfully upgraded" | `##installer.appKey.write.error####installer.appKey.set.value##` | 34 of 34 requests HTTP 500, `MissingAppKeyException` |
| No `app_key` line | Code 0, "Successfully upgraded" | `##installer.appKey.keyVariable.configFile.write.error####installer.appKey.keyVariable.missing.instruction##` | each request HTTP 500 |

The config was not changed in each case (the same sha256, opens with
`O_RDONLY` only). After root wrote a key and PHP-FPM restarted, the
site gave HTTP 200. So a missing key does not stop the upgrade, and the
exit code does not show it.

### No network

With `unshare -n`:

```
no network: rc=0 duration=11.8s
```

`rors` has 0 rows and there is no IP database file. The scheduled task
logs show `cURL error 6` for `download.db-ip.com` and `zenodo.org`. The
upgrade does not need the network. The two data sets come later, from
scheduled tasks.

### An interrupted upgrade

The backup before each run was that of note 0084: `mariadb-dump
--single-transaction`, and a copy of `files_dir`, `public` and the
config. The dump took 0.3 seconds (573,735 bytes).

| | Early `kill -9` | Late `kill -9` | `memory_limit=32M` |
|---|---|---|---|
| Stopped in | `I6093_AddForeignKeys`, 4.6 s | `I7135_CreateNewRorRegistryCacheTables`, 22.7 s | `I5716_EmailTemplateAssignments`, 8.8 s |
| Exit code | 137 | 137 | 255 |
| `versions`, core | 3.3.0.24 current | 3.3.0.24 current | 3.3.0.24 current |
| Tables | 114, schema changed (497 lines differ) | 133: 27 new, 8 gone | 129: 20 new, 5 gone |
| New files in `files_dir` | 0 | 5 | 0 |
| Site | HTTP 500 | HTTP 200 on the public pages, the login and the dashboard. The submissions API: HTTP 500 with the text of an SQL error | HTTP 500 |
| Second upgrade | Code 2, "Unknown column" in the pre-flight check | Code 2, "Unknown column" in the pre-flight check | Code 2 |

The memory failure:

```
label=M32 memory_limit=32M nostrace rc=255 duration=8.8s
PHP Fatal error:  Allowed memory size of 33554432 bytes exhausted (tried to allocate 2097152 bytes) in /usr/share/ojs/lib/pkp/lib/vendor/laravel/framework/src/Illuminate/Cache/FileStore.php
```

Thus:
- After each interruption, `versions` shows the old version. The
  database version does not show that an upgrade stopped.
- A second run of the upgrade on a half state fails. After the failed
  second run of the two `kill -9` cases, `versions` shows 3.3.9.9 as
  current.
- A half state can answer HTTP 200. OJS has no check that stops it.

### The restore

Two methods were compared with the state before the upgrade (a full
dump, a schema dump, the row count of each table, and the tree and the
sha256 of `files_dir`, `public` and the cache).

"Literal" is the text of note 0084 before this test: load the dump into
the database, copy the files and the config back, do not touch the
cache. "Clean" is: drop the database and create it again, load the
dump, synchronize `files_dir` and `public` with deletion of files that
are not in the copy, copy the config back, empty the cache.

| Half state | Method | Result | Upgrade after the restore |
|---|---|---|---|
| Early `kill -9` | literal | Identical (0 lines differ), 0.9 s | Code 0 in 73.5 s |
| Late `kill -9` | literal | 141 tables: 27 tables of the half state stay. 5 files stay | **Code 2**, "Table 'failed_jobs' already exists" |
| Late `kill -9` | clean | Identical (database, schema, files, `public`, cache: 0 lines differ), 1.3 s | Code 0 in 51.8 s |
| `memory_limit=32M` | clean | Identical | Code 0 in 102.5 s |

```
state R2-literal: ... tables 141; ... core=3.3.0.24
label=R2-literal-up memory_limit=2048M nostrace rc=2 duration=4.1s
ERROR: Upgrade failed: DB: SQLSTATE[42S01]: Base table or view already exists: 1050 Table 'failed_jobs' already exists
```

A dump has no `DROP TABLE` for a table that it does not contain. So the
restore must make a new database. Each upgrade that passed after a
restore gave the same schema (the same sha256 of the schema dump) as
the first upgrade.

### 3.5.0-5

- The 3.5.0-5 code on the 3.3 database: the upgrade stops with code 255
  in 7.3 seconds at `I5716_EmailTemplateAssignments`, with the
  `TypeError: Locale::setDefault()` of the first test. `versions` stays
  at 3.3.0.24. So 3.5.0-5 cannot upgrade a 3.3 database on this PHP.
- A new install of 3.5.0-5 (code 0, 120 seconds, 132 tables), then the
  upgrade to 3.5.0-6 with `kill -9` in the 10th of the 11 migrations:
  code 137, `versions` stays at 3.5.0.5, the schema is the same, 5 rows
  of `email_templates_default_data` differ. A second run passes (code 0
  in 0.7 seconds).
- For this database, the dump took 1.3 seconds (32,090,545 bytes) and
  the file copy 0.1 seconds (126,873,640 bytes). The clean restore took
  10.3 seconds (9.9 seconds for the database), and gave the identical
  state. These sizes are the ROR data and the IP database, not journal
  content.

## Other observations

A request to `127.0.0.1:80` or `[::1]:80` in the container gets HTTP
404. The `keel-health` nginx server of the image owns these addresses.
The page checks used the host name of the site on the global address.

## What this does not show

- A 3.2 database (the code refuses it; not run).
- A 3.3 build before 3.3.0-24, and a 3.4 database.
- A large journal. The durations here are for 19 submissions.
- A config that www-data can write.
- The package, `preinst`, `postinst` and `ojs-upgrade`. All steps were
  made by hand with scripts that do what the note says.
- A pair, Syncthing, and a slow link (netem).
- A browser. All requests were made with curl.
- A join of text columns across the two collations.

One trial run with `memory_limit` 32M and then 48M had no backup. Its
restore is not a result, and this file does not use it.

## State after the test

CT 9366 is stopped and not removed. It has two snapshots: the 3.3
database with the corrected `base_url`, and the new install of 3.5.0-5.
Nothing was published. The command logs of the test are with the
coordinator; this file holds the lines that the note uses. The
coordinator compared the report of the test with the logs before this
file was written.
