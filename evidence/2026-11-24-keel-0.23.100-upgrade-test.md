# Evidence: keel 0.23.100, the upgrade test of decision 0090 (the firewall in every mode)

Date: 2026-11-24. Site: BR2 test VM (`keel-pve-br2`, nested Proxmox VE
9.2.31, 4 vCPU, 12 GiB). The time zone is UTC. Status: draft.

No secret is in this file. Output is trimmed.

## Question

keel 0.23.100 is in the APT suite `trixie-testing`. `trixie` has 0.23.98.
keel 0.23.100 holds the firewall in every mode (decision 0097, keel PR 307
and PR 314). Decision 0090 requires an upgrade test on one node of each
published application before a core package goes to `trixie`. Does the
upgrade from 0.23.98 to 0.23.100 change an installed node, and what does the
firewall do on a node that declares no firewall?

The maintainer approved this run on 2026-11-24. The method is the method of
the test of 0.23.98 (`evidence/2026-11-24-keel-0.23.98-upgrade-test.md`),
with firewall checks added.

## Result

| Part | Result |
| --- | --- |
| The upgrade 0.23.98 to 0.23.100 (stage C) and a reboot (stage D), 13 applications | PASS on each application |
| Firewall across the upgrade and the reboot | no rule loaded, ruleset and listeners the same, `keel firewall check` exit 0 (`NOT APPLIED`) |
| `keel spec apply` on lnmp after the upgrade, with the image's own spec (step E) | **the node goes to `enforce`** and closes 2 sockets (see "Step E"). This follows rule B of 0097, but it is not "no rule". CT 9404 is kept for inspection |

VERDICT: PASS for the upgrade itself. Step E is reported for a decision
(see "Step E" and "Promotion").

## Method

Stages on each node (`run.sh`):

- A: the node as made from the published image (keel 0.23.96; Nextcloud
  0.23.97).
- B: `apt-get upgrade` from `trixie`, testing off: keel 0.23.98. The
  baseline.
- C: `upgrade.sh C` turns on `trixie-testing`, simulates
  `apt-get install keel=0.23.100`, stops when the simulation upgrades any
  other installed package (new packages are allowed: nftables could be new),
  installs, and turns `trixie-testing` off again. Just before and just after
  the install: the InvocationID of each unit (`units.sh`) and the firewall
  facts (`fw.sh`).
- D: `pct reboot`, 45 s of wait (the watch timer starts 30 s after the
  boot), then the same facts.
- E (lnmp only): `keel spec apply --system-only --non-interactive
  --skip-network` with the description of the node, unchanged.

`fw.sh` records: `keel firewall check` (output, exit), `nft list ruleset`,
the nft tables, the state of `keel-firewall.service`,
`keel-firewall-watch.timer`, `keel-firewall-watch.service`,
`nftables.service`, `crowdsec.service`, `crowdsec-firewall-bouncer.service`,
the nftables package, keel's firewall files, the listening sockets
(`ss -lntu`), and the keel-firewall lines of the journal. `fwdiff.sh`
compares two records: the ruleset without the elements of the sets (the
CrowdSec blocklist sets change by themselves all the time, with about
15000 elements), and the listeners.

**No `keel spec apply` in C and D.** In 0.23.100 the apply writes and loads
a firewall table in every mode. An apply in C would measure the apply, not
the upgrade. Thus `facts.sh` runs the apply in A and B only, and step E
measures the apply on one node.

In each stage, on each node: `facts.sh` (versions, `keel inspect`,
`keel diff`, failed units, `systemctl is-system-running`, Monit,
`nginx -t`, confconsole), the contract checks, and on WordPress, Odoo,
NodeBB and Nextcloud the login, write and upload checks through nginx (the
scripts of the 0.23.98 test).

A failed unit, a changed ruleset or a lost listener across the install stops
the run of that node (`run.sh`).

### CrowdSec and a restart of nftables.service

The CrowdSec tables stay across the install and the reboot on each node. A
restart of nftables.service is a different case. On core (0.23.100, after D)
`systemctl restart nftables.service` left only `inet filter`: the tables
`ip crowdsec` and `ip6 crowdsec6` were gone, and the bouncer (active) did
not load them again within 120 s (log 21-core-F-nftables-restart). The
control CT 9415 (core, keel 0.23.98, no candidate) gives the same result
(log 50-control-nftables-restart). Debian's `/etc/nftables.conf` starts
with `flush ruleset`. Thus the loss comes from Debian's file, not from the
candidate. keel's drop-in loads only keel's file, and there is none on these
nodes. This is finding 3 below.

## Step E: keel spec apply on lnmp with the image's own spec

After D, on CT 9404, `keel spec apply --system-only --non-interactive
--skip-network`. The description has no `firewall:` key (log 23-lnmp-E,
23-lnmp-E-detail). The apply exited 0 and wrote:

```
derived.firewall: enforce: each socket on an address that is not a loopback belongs to a unit of the manifests (decision 0097, B)
derived.firewall: closes udp 0.0.0.0:12321 of webmin.service (miniserv.pl): the manifests declare its process, not this port
derived.firewall: closes tcp *:36161 of syncthing.service (syncthing): the manifests declare its process, not this port
derived.firewall: 22000/tcp, 22000/udp of syncthing not opened: they are mesh ports, and the spec declares no network.overlay.wireguard
derived.firewall: 3306/tcp of mariadb not opened: they are mesh ports, and the spec declares no network.overlay.wireguard
derived.firewall: record /var/lib/keel/firewall/state: enforce and the hash of this ruleset ...: done
derived.firewall: write /etc/keel/firewall/keel-manifest.nft (enforce): public tcp 22, 80, 443, 12321 ...: done
derived.firewall: load it in one transaction, replacing table inet keel only ...: done
```

After the apply:

- `table inet keel` with `policy drop` in the chain `input`: accepts `lo`,
  established and related, ICMPv6, ICMP echo, DHCPv6 and DHCP client, and
  TCP 22, 80, 443, 12321.
- `keel firewall check` exit 0: "table inet keel is the one
  /etc/keel/firewall/keel-manifest.nft says".
- A TCP probe from the VM to the ULA address of the CT: before the apply
  22, 80, 443, 12321 and 36161 open; after the apply 22, 80, 443 and 12321
  open, 36161 closed or filtered.
- The listeners changed: Syncthing left `*:36161` and now listens on
  `127.0.0.1:22000`.
- No failed unit, `running`, the 21 contract checks pass. The other tables
  (`inet filter`, the CrowdSec tables) stay.

This is the table of section "The state" of 0097: "no `firewall:` key
(each published spec): `report`, then `enforce` by rule B: the first apply
that a person runs and whose sockets all belong to the manifests". Thus keel
does what 0097 says. But it is not "no rule if the spec declares no
enforce", the expectation of this test. By the rule of this test (a new
closed port on a node that declared nothing), step E is reported as a FAIL
for a decision. The upgrade itself did not cause it: the apply did, and only
an apply that a person runs does it.

Two points for that decision:

1. `keel diff` after the upgrade says the next apply writes `report`
   ("declared the ruleset apply renders from the manifests, report"), but the
   apply wrote `enforce`. The diff does not show rule B in advance.
2. On a one-node node the closed sockets have no user (Syncthing has no
   peer, the Webmin UDP port is its broadcast). On a node that an
   administrator uses in another way, the first apply closes each socket
   that the manifests do not name (0097, section on consequences).

CT 9404 is kept running for inspection. Every other CT is destroyed.

## Findings

1. **Step E: the first apply after the upgrade puts a node with no
   `firewall:` key in `enforce`** (rule B of 0097) and closes the sockets
   that the manifests do not name. `keel diff` says `report` before it.
   For a decision; node 9404 kept.
2. Nextcloud: a Debian upgrade of MariaDB makes `keel-nextcloud-cron.service`
   fail and closes the site for a time. Seen again in B, before the
   candidate (finding 1 of the 0.23.98 test).
3. **A restart of nftables.service removes the CrowdSec tables**, and the
   bouncer does not load them again within 120 s. The same on keel 0.23.98
   (control CT 9415). The cause is the `flush ruleset` of Debian's
   `/etc/nftables.conf`, which is enabled in each image. Not the candidate.
4. The other findings of the 0.23.98 test are seen again: the Proxmox
   `instance.fqdn` drift after a reboot, and
   `keel-database-position.service` restarts all the time on a one-node
   PostgreSQL node.

## Verdict

On each of the 13 applications, the upgrade from keel 0.23.98 to 0.23.100
by apt and a reboot leave the node as it was: the same contract checks and
web checks, no failed unit, the same ruleset and listeners, no rule loaded,
`keel firewall check` exit 0 with `NOT APPLIED`, and only the 7 keel timer
and path units restarted. The new units do not start on the upgrade;
`keel-firewall.service` and `keel-firewall-watch.timer` start at the next
boot and load nothing.

VERDICT: PASS for the upgrade.

## Promotion

For the upgrade itself, decision 0090 is met. Step E shows that the first
apply that a person runs after the upgrade puts each published node with no
`firewall:` key in `enforce`. This is decision 0097 as written, but the
maintainer should confirm it before the promotion to `trixie`, because each
installed node gets it at its next apply. The promotion is the maintainer's
act and is not part of this evidence.
