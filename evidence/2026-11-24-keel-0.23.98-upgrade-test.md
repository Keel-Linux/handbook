## Question

keel 0.23.98 is in the APT suite `trixie-testing` (apt#125). `trixie` has
0.23.97. Two questions:

1. Part A: with keel 0.23.98 from the archive, does a flat

   it (`evidence/2026-11-24-release-2026-11-19.md`).
2. Part B: decision 0090 requires an upgrade test on one node of each
   published application before a core package goes to `trixie`. Does the

## What changed in the candidate

keel 0.23.98 (keel#306, for apt#112): when the plain parent manifest at the
source holds another sha256 or is missing, `keel pull` reads
`PARENT-PARENT_SHA256.manifest`. A channel or a release revision does not
use these names.

Package contents (log 02, from archive.keellinux.org; each sha256 is the
same as the sha256 in the `Packages` index of its suite):

| --- | --- | --- |

| trixie-testing | 0.23.98 | `0e06e6ad…3c32` |

  out).
- Files with other content: `keel/__init__.py`, `keel/layers/pull.py`, the
  dist-info, the changelog, `DEBIAN/control` and `DEBIAN/md5sums`.
- `preinst`, `postinst`, `prerm` and `postrm` are the same. The

- The `postinst` restarts the keel timers and path units
  (`keel-mesh-*`, `keel-database-*`), as every keel upgrade does.

The chain of nextcloud resolves through the sha256 names. The cache of the

`nextcloud-5ea0dab6…`. On the mirror the plain `lnmp.manifest` says sha256

`lnmp-92608e24….manifest` says sha256 `92608e24…` (parent web

(`core-e32029de…`, `web-961d6bc9…`, `lnmp-7151751f…`); the nodebb chain is
the chain of the testing pointer.

**What is signed.** A flat pull checks no signature, and keel says so:
"flat layout: no channel pointer was read, so nothing here is signed for".
The mirror has no signed file for the flat layout: `nextcloud.tar.zst.hash`,
`nextcloud.tar.zst.sha256.asc` and `nextcloud.manifest.asc` answer 404, and
release 2026-11-19 has no `revision` file (log 14). `keel verify` checks the
sha256 and the size of each tarball against its manifest and each
`parent_sha256` along the chain; no layer has a `.hash` file, so it has no
signature to check. The signature check ran on the channel pull only: the
testing pointer verified against the channel key. Thus "full signature
verification" of the flat nextcloud pull is not possible with the files on
the mirror today. This is the same state as in the release evidence
(follow-ups 2 and 3 there).

## Part B: method

Stages, the same on each node (`run.sh`):

- A: the node as made from the published image.
- B: `apt-get update` and `apt-get upgrade` from the suites that are on
  (`trixie`, Debian). `trixie-testing` is off. This gives keel 0.23.97 and
  is the baseline.
- C: the candidate only. `upgrade.sh C` turns on `trixie-testing`, runs
  `apt-get -s install keel=0.23.98`, stops when the simulation names any
  other package, installs keel, and turns `trixie-testing` off again.
  `units.sh` records the InvocationID of each loaded unit just before and
  just after the install. A unit with a new InvocationID started or
  restarted.
- D: `pct reboot`, then the same checks.

In each stage, on each node:

- `facts.sh`: package versions; `keel inspect` (the `database` section and
  its report lines); `keel diff`; `keel spec apply --system-only
  --non-interactive --skip-network`; `systemctl is-system-running`; failed
  units; Monit; `nginx -t`; confconsole on a terminal.
- `contract_checks.py`: the contract's `services`, `urls`, `proofs` and
  `forbidden` items, as the runner does them, with the node's own secret
  files.
- On WordPress, Odoo, NodeBB and Nextcloud: a login, a write and an upload
  through nginx (see "Login, write and upload").

**"keel diff clean"** in this file means: no new drift compared with stage
B. A one-node node has drift that the setup gives (see "Findings that are
not the candidate"). `compare.py` compares the `keel diff` lines, the
`database` lines of `keel inspect` and the contract check lines of B with C
and with D.

Batches ran in parallel because the VM has 4 vCPU: the load average went to
25 during the stage B upgrades. Nothing failed because of this.

## Findings that are not the candidate

1. **Nextcloud: a Debian upgrade of MariaDB leaves
   `keel-nextcloud-cron.service` failed.** When the database stops during a
   run of `cron.php`, the unit fails and the node is `degraded`. The unit
   stays failed until it runs again with success or the node reboots. On
   CT 9414 the next run (07:13) did not start, because the site was closed
   during the upgrade (start condition `/run/keel-nextcloud/open`). Seen in
   B, before the candidate. 19.0-4 handles the loss of the write role, not a
   stop of the database. To file in keel-nextcloud.
2. **Proxmox writes the search domain of the host into `/etc/hosts` at each
   start of a CT.** `keel diff` then shows `instance.fqdn` drift until the
   next `keel spec apply`. Seen on keel 0.23.97 (control CT 9415) and on
   0.23.98. To follow up in keel (`network.managed_by: host`).

gave the same results after the upgrade to keel 0.23.98 as before it.

flat `keel pull nextcloud` passes, and the wordpress and nodebb pulls still
pass. The limits are in "Not tested".
