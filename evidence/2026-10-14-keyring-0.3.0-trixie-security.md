### 2a. Push to the public archive

```
# workstation
$ /tmp/keel-apt-tooling/bin/keel-publish-mirror --archive-only
keel-publish-mirror: https://archive.keellinux.org trixie-testing verifies
gpgv:                using EDDSA key D07DCCFE9A9991C9D700FF880B333BE515FA64B9
gpgv: Can't check signature: No public key
verify-repo: signature check failed for https://archive.keellinux.org/dists/trixie-security
keel-publish-mirror: the published archive did not verify against https://archive.keellinux.org
EXIT=7
```

The verify step of `keel-publish-mirror` runs
`$KEEL_APT_TOOLING_REMOTE/bin/verify-repo` on the build host. The default of
that variable is `/srv/keel-apt/apt` (d15cce5). That checkout does not have
apt#28. Its verifier checks every suite with the main key, so it cannot
verify trixie-security. The signature key in the output is the security
subkey, which is the correct key for that suite.

The verify step is the last step of `--archive-only`. The tree was already
on the public host. We did not change `/srv/keel-apt/apt`. We ran the same
check with the current verifier:

```

## 3. Verification from outside

The keyring files come from a fresh clone of Keel-Linux/keel-keys
(59edc21). The verifier is apt 38847bd on the workstation.

```
$ verify-repo --dist trixie --keyring keys/keel-trixie-main.asc https://archive.keellinux.org
verify-repo: InRelease and Release.gpg: good signatures with .../keel-trixie-main.asc
verify-repo: sha256 of main/binary-amd64/Packages matches Release
exit=0

$ verify-repo --dist trixie-security --keyring keys/keel-trixie-security.asc https://archive.keellinux.org
verify-repo: InRelease and Release.gpg: good signatures with .../keel-trixie-security.asc
verify-repo: sha256 of main/binary-amd64/Packages matches Release
exit=0

$ verify-repo --dist trixie-security --keyring keys/keel-trixie-main.asc https://archive.keellinux.org
gpgv: Can't check signature: No public key
verify-repo: signature check failed for https://archive.keellinux.org/dists/trixie-security
exit=4
```

Exit 4 is a signature failure, not a fetch failure (exit 3). The main key
cannot sign for trixie-security. This shows that the 2 roles are separate.

The role keys at the archive root:

```
$ curl -6 -fsS -O https://archive.keellinux.org/keel-<role>-keyring.asc
keel-archive-keyring.asc  AD0964BE3F09DED469A3B6B2148E951314703180 MATCH main
keel-security-keyring.asc D97E853FBDBB24492002067BA92969F1BF3B71C6 MATCH security
keel-testing-keyring.asc  9B3CFC527FAD0EA5298D84ED05B5A6FE7E3BA58A MATCH testing
keel-images-keyring.asc   E71DB9C3CA6AC18075395CC3ED3A709C4F3E2F3C MATCH images
```

Each file is also byte-identical to `keys/keel-trixie-<role>.asc` in
keel-keys.

The published `Packages` of trixie and trixie-testing were also examined.
keel-transition and keel-pve depend on `keel-archive-keyring (>= ...)`.
They do not have an exact version, so 0.3.0 does not remove them.

The stanza is the text that Keel-Linux/common#52 writes, after
`conf/turnkey.d/keel-apt` changes `Signed-By` to the binary keyring. We
added it to `/etc/apt/sources.list.d/security.sources`, after the Debian
stanza:

```

URIs: https://archive.keellinux.org
Suites: trixie-security
Components: main
Enabled: yes
Signed-By: /usr/share/keyrings/keel-security-keyring.gpg
