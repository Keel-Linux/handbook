## Client

The client ran on W and sent all requests to the VIP over HTTPS.

- A write every 0.5 s (5 s in the soak). A write counts as acknowledged only
  when the answer was 2xx and held an id.
- WordPress: a REST post, and at every tenth write a PNG as a multipart upload.
- Odoo: a JSON-RPC `res.partner` record, and at every tenth write an
  `ir.attachment`.
- A read every 0.5 s and a session check every 2 s.

After the runs, the test looked up each acknowledged id and each checksum on
both nodes. WordPress media also came back through the VIP (353 of 353 right).
Odoo stored attachments in the database. The file test changed this to files.

## Defects

### High

1. **A mesh join can stop for ever on C (Odoo: 2 of 2 builds, WordPress: 0 of
   2).** `keel mesh members` holds the sync and runs `systemctl start
   keel-vip.service`. That job waits for `etcd.service`, and its start timeout
   is infinity. etcd on C waits for B, but C has no WireGuard peer for B yet, and
   the upstream filter of BR2 stops B from connecting first. The peer is added
   only after the job ends. `keel spec apply` on C stopped with it, for at least
   13 minutes. Recovery: `systemctl cancel` of the `keel-vip` jobs on C.
2. **A replica spec with no `replication.primary` gives a site that stays at
   503, with no sign.** `00declarative` refuses the spec and the first boot hook
   stops. The WordPress marker and `wp-config.php` are not written, and the Odoo
   hook fails too. The system still says `running`, no unit fails, and `keel
   diff` shows no drift. Each CT crash that moved the VIP to B then gave 503 (2615
   failed writes in run 1). `keel/instance.pair.example.yaml` in both application
   repositories says that the replica uses "the same spec with role: replica",
   and that spec is the invalid one. The address of the primary is known only
   after the mesh exists, so the replica must boot after the primary joined.
3. **The Odoo image has no `/var/lib/odoo/filestore`.** The folder stays in
   `error` until the directory is made and Syncthing restarts. With the fix in
   place, `keel spec apply` also reports `write .stfolder: failed: Is a directory`
   (1 failed step).

### Medium

4. **Odoo stops for 158.7 s when the replica is cut.** WordPress stopped for 32.2 s
   in the same fault. The cause is not known. The test did not separate the
   synchronous commit wait from the Odoo workers.
5. **The first planned promote to a new Odoo node stopped writes for 190.1 s.**
   Later promotes took 34.9 s and 37.6 s. The cause is not known. A planned window
   must allow for this.
6. **A planned promote or a crash makes PostgreSQL reseed or rewind.** C reseeded
   6 times and B reseeded 4 times and rewound once. Each time it kept a dump. Ready
   took up to 263 s, against up to 111 s for MariaDB. The data was correct.
7. **WordPress sessions end at a failover or a promote.** The salts in
   `wp-config.php` differ between the 2 nodes. Users must log in again. Odoo
   sessions are files of one node, as its README says.

### Low

8. A raw binary `POST /wp-json/wp/v2/media` gets 403. A multipart upload works.
   The block is probably Coraza. The test did not confirm this.
9. On a node with no pair, `keel diff` exits 14 because of
   `declared paused, observed paused` and `filesync.peer`, if Syncthing is on.
10. `instance.fqdn` shows drift after a restart (`.keel.test` declared, `.pop.coop`
    observed). The host names and search domain of the test may cause this.
11. `keel-database-follow` is a failed unit on the replica until the first claim.
    `keel vip promote` right after the third join gave `etcd did not answer`. It
    worked when run again later.

## What went wrong in the test

- **Run 1 is not counted.** Its replica specs had no `replication.primary`
  (defect 2). B could not serve, so writes on B were not tested. No acknowledged
  record was lost in it. The test destroyed those CTs and built new ones. Its
  acknowledged Odoo data was not checked.
- **A driver error in run 1** started the wrong CT, so C stayed stopped for about
  5 minutes.
- **Odoo attachment location.** The test set `ir_attachment.location` to `file` by
  hand for the Syncthing test. The default is `db`, so Syncthing does not carry
  attachments by default.
- **Local edit.** The test left the edited file on C. `keel diff` on C reports it.

## What this test does not show

- A browser. The client used a test user agent, and the block editor, the Odoo web
  client and the Anubis challenge were not used. Odoo reports were not tested.
- Load at scale. One client made about 2 writes each second. The BR1 load average
  was about 13.
- A cut of BR1. The client is on BR1, so only BR2 was cut.
- The fixes that are not merged (keel#191, keel#252, keel#107, keel#190, keel#167,
  decision 0070) and keel#110 in 0.23.69.
- An alert that was sent. The CTs have no monitor channel.
- BR3-THIN, and Nextcloud.
