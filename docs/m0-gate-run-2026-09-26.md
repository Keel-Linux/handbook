# M0 gate run, 2026-09-26

First execution of docs/m0-gate.md against the organization forks. Both
builds ran on the project build host (TKLDev 19.0, trixie, kernel
6.12.107+deb13-amd64), the same day, from the same bootstrap and with
`SOURCE_DATE_EPOCH=1700000000`. Tools on the host: fab 1.1.1, deck 2.1.1,
pool 1.2.1, turnkey-chroot 1.1.2, debootstrap 1.0.141, squashfs-tools
1:4.6.1-1, xorriso 1.5.6-1.2+b1, syslinux-utils 3:6.04~git20190206-3.1.
`postfix` was inactive on the host before the run.

## Verdicts

- Gate 1, equivalence: **pass.** Package lists identical (412 packages).
  49 of 33,684 regular files differ, all install-time state; none is
  traceable to a source difference between the two trees. The allow-list
  in m0-gate.md is now frozen to what was observed here.
- Gate 2, packing: **pass for the squashfs, fail for the ISO** with fab
  1.1.1. Two packings of the same `root.patched` give the same squashfs
  hash; the ISOs differ in 178 bytes (the random isohybrid MBR ID and the
  ISO 9660 and Rock Ridge timestamps of files copied at packing time).
  m0-gate.md said this gate was already met; that statement was too broad
  and is corrected. The organization's fab fork already carries the fix
  (share/product.mk: `--set_all_file_dates @$(SOURCE_DATE_EPOCH)` and
  `isohybrid --id`), but it is not what the build host runs: tkldev-setup
  installs fab from apt, so both builds used the upstream 1.1.1 package.

The appliance repository is `keel-core` but the checkout is
`products/core`: product.mk derives `ISOLABEL` and turnkey.mk derives
`HOSTNAME` from the directory basename, so a `products/keel-core` checkout
would change `/etc/hostname`, `/etc/hosts` and the ISO label and fail the
equivalence gate by construction. tkldev-setup does this mapping itself
(`keel-tkldev-setup core` clones `keel-core` into `products/core`).

Bootstrap: `keel-linux/bootstrap` does not exist, so the local bootstrap
build that tkldev-setup falls back to (a clone of `$GIT_REMOTE_URL/bootstrap`)
cannot work on the organization remote. The existing
`/turnkey/fab/bootstraps/trixie-amd64` was copied (`cp -a`) to
`/turnkey/fab-keel/bootstraps/trixie-amd64` before running tkldev-setup,
which then reported "exists, skipping download". Same bootstrap bytes on
both sides, which is also why `/etc/machine-id` is identical in both images
(it is written by the bootstrap, not at install time).

## Gate 2 detail

The second packing removed `build/stamps/cdroot`, `build/cdroot` and
`build/product.iso` and ran `make` again with the same environment.

- squashfs: bit-identical (0 differing bytes). mksquashfs 4.6.1 reads
  `SOURCE_DATE_EPOCH` for the filesystem creation time and clamps newer
  mtimes to it.
- ISO: 178 differing bytes. 4 at offsets 440 to 443, the MBR disk ID that
  `isohybrid` picks at random when `--id` is not given (85 4b 79 47 vs
  e3 f8 c1 3a; upstream 5a 66 be 2d). 174 in sectors 16 to 28: the ISO
  9660 recording dates and Rock Ridge TF timestamps of the root, `isolinux`
  and `live` directory records. xorriso 1.5.6 honours the epoch for the
  volume descriptor dates (both packings show 2023-11-14 22:13:20) but sets
  `all_file_dates` to `set_to_mtime`, and product.mk copies isolinux
  modules, vmlinuz and initrd with plain `cp` and writes the squashfs at
  packing time, so those files carry the packing time as mtime. The cdroots
  checkout mtime shows the same way (upstream checkout 2026-09-22, fork
  2026-09-26).

Verdict for gate 2: partial. Met for the squashfs, not for the ISO with fab
1.1.1. The fix is the fork's product.mk (keel-linux/fab master 7ea960a:
`XORRISO_DATE_OPTS := --set_all_file_dates @$(SOURCE_DATE_EPOCH)` and
`ISOHYBRID_OPTS := --id $(SOURCE_DATE_EPOCH)`), which has to be built as
the fab package the build host installs before the gate can be re-measured.
That is the next step and is recorded in m0-gate.md.

Two notes from the run. First, when the `root.sandbox` stamp is removed,
`deck build/root.patched` has to run before `make`: layering the sandbox
releases the parent deck's mount and `mksquashfs` then packs an empty
directory (4,096-byte squashfs, 56,623,104-byte ISO, two-second `make`). One
such run happened here and was discarded. Second, that empty squashfs hashes
to `8c339c02...` with the epoch, which is the value ../TKL/plan/06 recorded
as reproducible on 2026-09-22; that measurement most likely packed an empty
root as well and should be re-read against this one.
