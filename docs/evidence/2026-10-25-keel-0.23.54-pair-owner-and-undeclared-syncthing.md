## 1. keel#225: owner after the initial replication

1. Syncthing on B was stopped. On C, as `www-data`, a nested tree was
   made in `wp-content/uploads`: 2 years of 6 months with a `deep/er`
   level each, and `2026/10/a/b/c/d`. Together there were 75 files and
   45 directories. Syncthing on B was started again.
2. The tree arrived complete (75 files, 45 directories). Before the
   promote, 60 entries under the 4 replicated paths were owned by
   `syncthing` (the defect of keel#225: a directory arrives before its
   parent has the application owner).
3. `keel database promote` on B. B became the primary at epoch 2. The
   flip printed `syncthing: 4 folder(s) primary`, and the log of the
   follow said: `syncthing: the application owner restored on 60
   replicated entries`.
4. After the promote, 0 entries under the 4 replicated paths were owned
   by `syncthing` (`find ... -user syncthing -o -group syncthing`).
5. On the new primary, `wp --path=/var/www/wordpress media import
   t9.png` as `www-data` succeeded (attachment 4,
   `uploads/2026/10/t9.png`). The file replicated to C, the former
   primary, with the identical sha256 `57cda64c...` and `www-data`
   ownership.

## 2. keel#224: a spec without `overlays.syncthing`

### `keel spec apply` refuses

On a pair node that already recorded the overlay, the spec check refuses
before any change:

```
Error: /etc/keel/instance.yaml: overlays.syncthing: not declared; every overlay of the chain of wordpress is written out, enabled or disabled (decisions 0027, 0041)
exit=3
```

`keel spec apply --system-only`, `--dry-run` and a plain `keel spec apply`
gave this error with exit 3. A spec with `syncthing: disabled` was
accepted. `keel database promote` ran the same check and also exited 3
with this spec.

On a fresh CT (9229, made from a spec without the key, then keel
0.23.54), the check of keel#224 answers. The overlay is not recorded
yet, so the manifest default applies and the check of the file
replication refuses:

```
Warning: ... overlays.syncthing: not declared (default: enabled): the chain of wordpress gained it after this spec was last applied ...
Error: overlays.syncthing: not declared in the spec, and the appliance replicates files for cloud_advanced: write `overlays.syncthing: enabled` (or `disabled`) ...
exit=3
```

### `keel database follow` warns, alerts once, and does the role change

The key was removed from the spec of C (a replica). A manual
`keel database follow` printed `WARNING: file replication is off for this
pair: overlays.syncthing: not declared ...` and exit 0. Then B was
stopped (`pct stop`). The etcd controller moved the VIP to C. The path
unit ran `keel database follow` on C, which:

- printed the warning;
- drained and promoted the database (`read_only` OFF, "takes writes");
- wrote `replicates=database` in the role file (files off);
- left the marker `/var/lib/keel/database/filesync-undeclared`.

The next follow runs printed the warning again and no second alert
line: one alert for the whole condition. The key was written back and
`keel database follow` ran: the marker was removed, the role file said
`replicates=database,files` and the folders were `sendonly`. B started
again and rejoined as a replica with no operator step.

## Defect found: file replication does not resume after a reboot (keel#228)

After `pct start` of B, the database replication resumed by itself, but
the files did not. Syncthing on B had `paused: true` on the peer device,
and C logged `Failed to exchange Hello messages ... EOF` every 20 s.
The cause is the start-paused edit of the unit (`START_PAUSED`): its
`sed` pauses every `<paused>false</paused>` of config.xml at each boot,
the devices too. The first proven follow unpauses the folders and not
the devices. Workaround used in the test: `PATCH
/rest/config/devices/<peer id>` with `{"paused": false}`. The files
replicated again at once. keel#228 is open.

## Limits

  `/etc/keel/monitor.json` secret (`no alert sent (/etc/keel/monitor.json:
  secret file not found)`), as in the test of 2026-10-24. The log line
  and the once-only marker are the evidence.
- The image of the build holds keel 0.23.52. The test installed keel
  0.23.54 from trixie-testing in each CT. An image build with 0.23.54
  needs the Core layer to be built again.
- The test used WordPress only. The witness CT showed `keel diff` exit
  14 (it is a stand-alone node with no replication, not a pair node).
