# Evidence: Odoo 19.0-11 and keel 0.23.49, a fast stop of PostgreSQL (keel#219), a release test across 2 sites

Date: 2026-10-19. The time zone is UTC.
Decisions: 0054, 0059, 0061. The coordinator asked to test a theory for the
PostgreSQL hang of the 19.0-8 bootstrap (`2026-10-19-odoo-19.0-10-keel-0.23.48.md`,
"The hang"): a smart shutdown waits for every client, so an idle client holds a
stop. The CTs 9054 and 9062 were not read or touched. No secret is in this file.

## Result

| Item | Result |
| --- | --- |
| The theory | **Reproduced.** On the real standby (CT 9149) with one idle client (a `psql` that runs `pg_sleep(600)`, as the poll of `serve.py` is one), `kill -TERM` of the postmaster, a smart shutdown: alive after 12 s, and at the end of the test. Then `kill -INT`, a fast shutdown: gone in under 5 s. So a stop that sends SIGTERM to the postmaster can hold for `TimeoutStopSec`, 1 h in Debian's unit |
| What is not proven | That an idle client was the one that held the 19.0-8 bootstrap. The race that sent the SIGTERM (apply restarts the unit while follow stops it) was never reproduced. keel#219 says so |
| The fix | keel 0.23.49 (keel#220): the drop-in `keel-stop.conf` sets `KillSignal=SIGINT` and `TimeoutStopSec=120s`. A fast shutdown does not lose committed data, and the final SIGKILL after 120 s is crash safe, because PostgreSQL recovers from its WAL at the next start. 3 tests were written first and failed before the drop-in existed (`TestFastStop` in `tests/test_packaging.py`); the 11 CI jobs passed |
| Image | `debian-13-keel-odoo_19.0-11_amd64.tar.zst`, sha512 `e967096bac3a406e`, keel-odoo `2562504`, keel 0.23.49. The image build per merge booted it (image-gate run 31) and promoted the same files; the 3 CTs started from them (same sha512 on both PVE hosts, in testing and in the staged tree). The main key and the images key each verify it alone |
| Unit on the 3 CTs | `systemctl show postgresql@17-main`: `KillSignal=2` (SIGINT) and `TimeoutStopUSec=2min` on W, B and C |
| A stop with an idle client, on the 19.0-11 standby | `systemctl stop` took 0.2 s with the client held open. This is the normal path (ExecStop, a fast shutdown) and was fast before too: it shows that the drop-in breaks nothing, not that it fixes the race |
| Pair bootstrap | 3 of 3 CTs complete the first boot; `systemctl --failed` is empty; the pair forms, with no wait. Third bootstrap in a row with no hang |
| Failover with writers | cut of the holder C; VIP lands on B 19.14 s after the cut; first DB write 1.75 s after the VIP; Odoo write 3.82 s after the VIP; 0 acknowledged writes on C after the cut; 0 of 1384 ids lost; 0 of 524 Odoo writes lost; both nodes hold 1385 test rows and 524 partners; the attachment of 400000 bytes has the same sha256 after the failover; `keel diff` shows no drift on the 3 nodes |

## Open

- The race of keel#219 (apply restarts the unit while follow stops it) is
  still there. The drop-in bounds its cost to 120 s instead of 1 h, and does
  not remove it. Taking the lock of follow in the restart of apply would.
- Test CTs left running: 9144 (BR1, witness), 9148 (BR1) and 9149 (BR2).
